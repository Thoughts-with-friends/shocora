# 8.4 The File System: FS and FSA

[← 8.3 The round trip](08_3_round_trip.md) · [8. IOSU and IPC](08_0_iosu_ipc.md) · next: [8.5 The other services →](08_5_services.md)

The [file system (FS / FSA)](../guide/wiiu_term.md#t8-10) is the busiest IOSU service by far:
a big game opens thousands of files while it runs. This section shows the two API layers, the
paths a game sees, and the result codes it gets back.

## 8.4.1 Two layers: FS and FSA

```text
   game
    │
    │  FS*  (coreinit "FS" API)                      FSA*  (low-level API)
    │  FSAddClient, FSOpenFile[Async],               FSAAddClient, FSAOpenFileEx,
    │  FSReadFile[Async], FSGetStat …                FSAReadFile, FSAGetStat …
    │  ── command blocks, async, error masks         ── plain synchronous calls by handle
    ▼                                                  │
   coreinit FS client  ───────── IOCTL / IOCTLV ───────┴──────► /dev/fsa  (IOS-FS on the ARM)
```

- `FS*` is the comfortable API almost every game uses: it adds command blocks, an async mode,
  per-call error handling, and a queue per client.
- `FSA*` is closer to the device: each call is one request to `/dev/fsa` on a handle the game
  opened itself. System software and some newer titles use it.

Both are implemented in shocora: `FS*` in
[core/cafe_os/src/coreinit/fs/](../../core/cafe_os/src/coreinit/fs/mod.rs), `FSA*` in
[core/cafe_os/src/coreinit/fs/fsa_client.rs](../../core/cafe_os/src/coreinit/fs/fsa_client.rs).

## 8.4.2 Client and command block

```text
   FSClient   (0x1700 bytes, game-allocated)        FSCmdBlock (0xA80 bytes, game-allocated)
   ┌────────────────────────────────────┐           ┌──────────────────────────────────────┐
   │ one per thread / subsystem that    │  queues   │ one per request in flight            │
   │ does file I/O: the /dev/fsa handle,│◄──────────│ holds the request's IPC block, its   │
   │ current directory, the command     │           │ buffers, the async parameters and    │
   │ queue, error state                 │           │ the result                           │
   └────────────────────────────────────┘           └──────────────────────────────────────┘

   FSInit()                          once per process
   FSAddClient(&client, errMask)     once per client
   FSInitCmdBlock(&block)            before (re)using a block
   FSOpenFile(&client, &block, "/vol/content/a.bin", "r", &fh, errMask)
```

Sizes are Cemu's (`FS_CLIENT_BUFFER_SIZE` 5888, `FS_CMD_BLOCK_SIZE` 2688). The game allocates
these structures and keeps them for a long time; the library stores its private state inside
them, so an emulator has to keep that state where the game expects it, not in a host-only
table that a save state or a re-used block would lose.

## 8.4.3 One file read, both sides

```text
   game                     coreinit FS (client side)            IOSU FSA (/dev/fsa)
   ────                     ─────────────────────────            ───────────────────
   FSAddClient ───────────► FSClient (state in guest memory) ──► OPEN /dev/fsa
   FSOpenFileAsync ───────► FSCmdBlock queued ─► IOCTL OPENFILE ─► resolve /vol/... path
                                                                   on the mounted volume
                            ◄── result + handle ──────────────────
   callback / message ◄──── FS completion
   FSReadFile ────────────► IOCTLV READ (buffer, size, count) ───► bytes into MEM2
   FSCloseFile ───────────► IOCTL CLOSEFILE ─────────────────────► handle released
```

The FSA command numbers, as named in Cemu's `FSA_CMD_OPERATION_TYPE`
(`Cafe/IOSU/fsa/fsa_types.h`):

```text
  ┌──────┬──────────────┐  ┌──────┬──────────────┐  ┌──────┬──────────────┐
  │ 0x05 │ CHANGEDIR    │  │ 0x0C │ REWINDDIR    │  │ 0x13 │ ISEOF        │
  │ 0x06 │ GETCWD       │  │ 0x0D │ CLOSEDIR     │  │ 0x14 │ GETSTATFILE  │
  │ 0x07 │ MAKEDIR      │  │ 0x0E │ OPENFILE     │  │ 0x15 │ CLOSEFILE    │
  │ 0x08 │ REMOVE       │  │ 0x0F │ READ         │  │ 0x17 │ FLUSHFILE    │
  │ 0x09 │ RENAME       │  │ 0x10 │ WRITE        │  │ 0x18 │ QUERYINFO    │
  │ 0x0A │ OPENDIR      │  │ 0x11 │ GETPOS       │  │ 0x19 │ APPENDFILE   │
  │ 0x0B │ READDIR      │  │ 0x12 │ SETPOS       │  │ 0x1A │ TRUNCATEFILE │
  └──────┴──────────────┘  └──────┴──────────────┘  │ 0x1E │ FLUSHQUOTA   │
                                                    └──────┴──────────────┘
```

`QUERYINFO` covers several questions (free space, device info, stat of a path), selected by a
sub-type in the request.

## 8.4.4 The paths a game sees

```text
   /vol/code          its own executables, RPX + RPLs            read-only   (code/ folder)
   /vol/content       its data files                             read-only   (content/ folder)
   /vol/meta          icon, banner, meta.xml                     read-only   (meta/ folder)
   /vol/save          its save data                              read/write  ── chapter 10
   /vol/aoc…          downloadable content, after nn_aoc mounts it
   /vol/storage_mlc01 internal storage (system titles; other titles' saves via nn_save)
   /vol/external01    SD card, after FSMount
```

- `/vol/code`, `/vol/content` and `/vol/meta` map to the [title](../guide/wiiu_term.md#t8-1)'s
  [`code/`](../guide/wiiu_term.md#t8-3), [`content/`](../guide/wiiu_term.md#t8-4) and
  [`meta/`](../guide/wiiu_term.md#t8-5) folders. An [update](../guide/wiiu_term.md#t8-7)
  replaces files in them; [DLC](../guide/wiiu_term.md#t8-8) appears as its own volume.
- `/vol/save` is backed by the user's [save data](../guide/wiiu_term.md#t8-9) folder in
  [`mlc01`](../guide/wiiu_term.md#t8-14). How saves are organised per user is in
  [10. Titles, Storage and Saves](10_titles_storage.md).
- The game never sees host paths or the console's real device names: everything goes through
  these mount points. That is what lets an emulator back them with folders on the PC.

One detail games depend on: `FSChangeDir` sets a per-client working directory, and relative
paths are joined to it. `FSGetCwd` returns it with a trailing slash; Paper Mario: Color Splash
concatenates that with a relative path and crashes if the slash is missing.

## 8.4.5 Result codes

There are two sets of negative codes, one per layer:

```text
   FS_STATUS (what FS* returns to the game)        FSA status (what /dev/fsa returns)
   ┌──────────────────┬─────────┐                  ┌──────────────────────┬────────────────┐
   │ OK               │  0      │                  │ OK                   │  0             │
   │ END (no more)    │ −2      │                  │ NOT_INIT             │ −0x30000 − 0x01│
   │ MAX (handles)    │ −3      │                  │ END_OF_DIRECTORY     │ −0x30000 − 0x04│
   │ EXISTS           │ −5      │                  │ END_OF_FILE          │ −0x30000 − 0x05│
   │ NOT_FOUND        │ −6      │                  │ MAX_FILES            │ −0x30000 − 0x13│
   │ NOT_FILE         │ −7      │                  │ ALREADY_EXISTS       │ −0x30000 − 0x16│
   │ NOT_DIR          │ −8      │                  │ NOT_FOUND            │ −0x30000 − 0x17│
   │ PERMISSION_ERROR │ −10     │                  │ PERMISSION_ERROR     │ −0x30000 − 0x1A│
   │ FATAL_ERROR      │ −0x400  │                  │ INVALID_PATH         │ −0x30000 − 0x22│
   └──────────────────┴─────────┘                  └──────────────────────┴────────────────┘
                     (values as in Cemu's fsa_types.h; both lists are excerpts)
```

The FS layer maps FSA codes to `FS_STATUS` codes before returning.

## 8.4.6 Error masks: when an error is fatal

```text
   FSOpenFile(client, block, path, "r", &fh, errMask)
                                               │
       result NOT_FOUND ─► is NOT_FOUND in errMask?
                              ├─ yes ─► return −6 to the game, it handles it
                              └─ no  ─► the system shows an error screen and stops
```

Each `FS*` call takes an error mask: the list of errors the game promises to handle. Any other
error is treated as fatal. Games pass "not found" in the mask when probing for optional files
(an update, DLC, a save that may not exist yet) and leave it out when a file must exist. An
emulator that returns a wrong error code can therefore turn a harmless miss into a crash
screen.

## 8.4.7 In shocora

```text
   FSOpenFile / FSAOpenFileEx (HLE, Rust)
        │
        ▼
   wiiu_iosu::Fsa::open_file(path, mode)          core/iosu/src/fsa.rs
        │  handle table, positions, directory iterators
        ▼
   wiiu_fs::Vfs  ─ mount table: /vol/code, /vol/content, /vol/save … ─► host folders / archives
```

[core/iosu/src/fsa.rs](../../core/iosu/src/fsa.rs) keeps open files and directories by handle;
it holds only paths, not host file handles, so mounts can be swapped (for example when graphic
packs replace content files) without breaking open files. Async calls complete through the
guest's callback or message queue in the order 8.3.4 describes; when the game's queue is full,
the completion is parked and delivered once a slot frees up, as the console's FS thread would.

## Summary

- `FS*` = client, command block, async, error masks; `FSA*` = direct device calls.
- The game sees only `/vol/...` mount points; that is the seam where an emulator plugs in host
  folders.
- Exact result codes matter because of error masks.
