# Wii U Terms, Explained for Beginners

This page is for anyone who wants to understand how a Wii U emulator works, even if you have never looked inside a game console before. Each term gets one row in a table:

- **In plain words**: what the thing is.
- **Picture it as**: an everyday comparison to help you imagine it.
- **Why it matters**: what it does on a real Wii U, and what shocora (this emulator) does about it.
- **For intermediates**: for people who play PC games and write some code but know nothing about consoles or emulators. It compares the term with things you already know (Windows, DirectX, `std::thread`…) and says how it connects to other terms.
- **For experts**: registers, API names, data layouts and implementation details, for when you read the code.

Read a row from left to right: each column goes one step deeper than the one before.

Rows are numbered by chapter (2.5 is the fifth term of chapter 2), so you can point to a term. Linked terms such as [Register](#t2-9) jump to their own row.

You don't need to read it in order. Start with "The big picture", then look up words as you meet them.

## 1. The big picture: what an emulator does

A game console is a small computer with its own processor, graphics chip, memory and operating system. A game is a program written only for that machine. Your PC can't run it directly: it speaks a different "language" (instruction set), has a different graphics chip, and doesn't have the Wii U's operating system.

An **emulator** is a program that pretends to be the console. Imagine a translator, a stage crew and a fake post office all working together so that an actor (the game) believes it is performing on its usual stage:

1. **The CPU part** reads the game's instructions and does the same work on your PC's processor (the translator).
2. **The graphics part** reads the drawing orders the game sends to the Wii U's graphics chip and redraws the picture with your PC's graphics card (the stage crew).
3. **The operating-system part** answers the game's requests ("open this file", "start a thread", "play this sound") the way the Wii U's system software would (the post office).

When all three keep up with the game, it runs at full speed. When one falls behind, the game stutters or slows down.

## 2. Hardware: the parts inside the console

The Wii U has three main chips: a **CPU** (the thinker), a **GPU** (the painter) and a small **security processor** (the gatekeeper). Around them are memory, flash storage, and the controllers.

| # | Term | In plain words | Picture it as | Why it matters | For intermediates | For experts |
| ---: | --- | --- | --- | --- | --- | --- |
| <a id="t2-1"></a>2.1 | CPU | The chip that runs the game's program, one instruction after another. | The brain that follows a recipe step by step. | Everything a game "decides" (physics, enemies, menus) happens here. | Your PC's CPU in principle, but much older and simpler: no SIMD like SSE/AVX, small [caches](#t2-5), three [cores](#t2-3). | In-order-issue superscalar [PowerPC](#t2-7) 750 derivative; 32 KiB L1 I/D per [core](#t2-3), 32-byte lines; no AltiVec. |
| <a id="t2-2"></a>2.2 | Espresso | The name of the Wii U's [CPU](#t2-1), made by IBM. It has three [cores](#t2-3) running at about 1.24 [GHz](#t2-4). | Three cooks sharing one kitchen. | shocora has to imitate all three cooks at once and fast enough. This is the hardest part of running Breath of the Wild well. | A descendant of the GameCube and Wii CPUs. Each core is far weaker than a modern PC core, but emulating it costs many host instructions per guest instruction ([Interpreter](#t11-1), [JIT (just-in-time compiler) / recompiler](#t11-2)). | Three 750CL-derived [cores](#t2-3) at 1.243125 [GHz](#t2-4) on a 248.625 MHz bus; L2 is 512 KiB / 2 MiB / 512 KiB for cores 0 / 1 / 2. |
| <a id="t2-3"></a>2.3 | Core | One independent worker inside a [CPU](#t2-1). The Wii U has core 0, 1 and 2. | One of the three cooks. | Games split their work across cores. Core 1 is the "main" one: it starts the game and usually sends the drawing orders. | Like the cores of a PC CPU, but the game decides which [threads](#t4-10) run where ([Affinity](#t4-13)). Core 1 has the largest [Cache](#t2-5) and runs the main game loop. | Core number is read from SPR UPIR (1007); `OSGetCoreId` returns it. shocora's `CALLBACK_CORE` / main core is core 1. |
| <a id="t2-4"></a>2.4 | Clock speed (GHz) | How many basic steps a [core](#t2-3) takes per second. 1.24 GHz = 1.24 billion. | How fast a cook chops. | A PC [core](#t2-3) is much faster, but imitating a different [CPU](#t2-1) costs many PC steps per Wii U step. | Games measure time with the [Time base](#t2-13), not by counting cycles, so the emulator doesn't need to match the clock speed, only the passage of time. | [Time base](#t2-13) runs at bus/4 = 62.15625 MHz regardless of the [core](#t2-3) clock; `OSSecondsToTicks` uses that rate. |
| <a id="t2-5"></a>2.5 | Cache | A small, very fast memory right next to a [core](#t2-3) that keeps recently used data. | The cook's cutting board, compared with the fridge across the room. | Real hardware detail the game sometimes relies on. Games tell the cache when to [save data](#t8-9) back to memory, and shocora uses those hints to know what changed. | The same idea as the L1/L2 caches in your CPU, but the Wii U's GPU doesn't see what is still in the CPU's cache. Games must flush it before the GPU reads data, so those flushes tell the emulator what changed ([Cache line](#t3-8)). | Games manage coherence with `dcbf`/`dcbst`/`dcbi`/`dcbz` and `DCFlushRange` etc.; shocora's memory is coherent, so these only feed the [GPU](#t2-15) write tracker. |
| <a id="t2-6"></a>2.6 | Instruction set (ISA) | The "language" of commands a [CPU](#t2-1) understands. | The language a recipe is written in. | The Wii U speaks [PowerPC](#t2-7); your PC speaks x86-64 (or ARM). shocora must translate. | Like a file format for code: x86-64 binaries don't run on ARM phones, and Wii U binaries don't run on x86. Translating between them is the job of the [JIT (just-in-time compiler) / recompiler](#t11-2). | Fixed 32-bit instructions; shocora decodes by primary/extended opcode into an `Opcode` enum shared by the [interpreter](#t11-1), disassembler and [JIT](#t11-2). |
| <a id="t2-7"></a>2.7 | PowerPC | The [instruction set](#t2-6) of the Wii U's [CPU](#t2-1) (also used by the GameCube, Wii, PS3 and old Macs). | Japanese, when your cook only reads English. | Every instruction of the game is a PowerPC instruction that shocora interprets or translates. | A RISC instruction set: every instruction is 4 bytes, with many [registers](#t2-9). Simpler to decode than x86, which helps the [Interpreter](#t11-1). | 32 GPRs, 32 FPRs, CR (8×4 bits), LR, CTR, XER, FPSCR, MSR, SRs and ~1024 SPRs; branches via `bc`/`bclr`/`bcctr`. |
| <a id="t2-8"></a>2.8 | Big-endian / little-endian | The order in which the bytes of a number are stored. Big-endian puts the "big end" first. | Writing a date as 2025-12-31 versus 31-12-2025: same date, opposite order. | The Wii U is big-endian, PCs are little-endian. shocora flips the byte order whenever the game reads or writes memory. | Like network byte order in socket programming (`htonl`): every 16/32/64-bit value in guest memory must be byte-swapped when the host reads or writes it. | [Guest](#t1-2) loads and stores are big-endian; the [JIT](#t11-2) emits `bswap` around [host](#t1-3) loads/stores of guest memory. |
| <a id="t2-9"></a>2.9 | Register | A tiny storage slot inside a [core](#t2-3) holding the value it is working on right now. | The few numbers a cook keeps in their head while cooking. | When the [emulator](#t1-1) switches between game [threads](#t4-10), it saves and restores all registers. | Think of them as the CPU's local variables: a few dozen named slots (r0–r31 for integers, f0–f31 for floats, plus special ones for return addresses and loop counters). A [thread](#t4-10)'s state is mostly its registers. | `CpuState` is saved into the [thread](#t4-10) record on every switch; `clone_from` reuses the SPR storage to avoid an allocation per switch. |
| <a id="t2-10"></a>2.10 | Paired singles | A Wii U [CPU](#t2-1) feature that does two small math operations at once. | Chopping two carrots with one stroke. | Games use it for 3D math. shocora must reproduce it exactly or objects end up in the wrong place. | A two-lane float SIMD, a tiny version of SSE. Each float [register](#t2-9) holds two values; vector maths in games (positions, matrices) is built on it. | FPRs hold ps0 (double) and ps1 (single); `ps_*` ops act on both lanes, `psq_l`/`psq_st` load and store quantized pairs; FPSCR rounding and flush-to-zero matter. |
| <a id="t2-11"></a>2.11 | GQR | Settings that tell the [CPU](#t2-1) how to squeeze numbers into fewer bytes and unpack them again. | The packing instructions for a suitcase. | Lets games store data compactly; shocora follows the same rules when loading and storing. | Settings registers that let one load instruction convert, say, a 16-bit integer into a float scaled by 1/256. A cheap way to store compressed vertex data, used with [Paired singles](#t2-10). | SPRs 912–919; each holds load and store type (float, u8, u16, s8, s16) and a 6-bit scale (×2^±n). |
| <a id="t2-12"></a>2.12 | Locked cache (LC) | Part of each [core](#t2-3)'s [cache](#t2-5) that a game can use as its own small, ultra-fast memory. | A private shelf next to the cook. | Some games copy data there for speed. shocora treats it as normal memory. | Part of the [Cache](#t2-5) reserved as a 16 KB scratchpad the game controls itself, with DMA copies in and out, like a manually managed cache. | Enabled by HID2[LCE]; filled and drained by DMA through SPRs DMAU/DMAL (`LCLoadDMABlocks`, `LCStoreDMABlocks`); mapped at effective `0xE0000000`. |
| <a id="t2-13"></a>2.13 | Time base | A counter that ticks about 62 million times per second, from power-on. | The kitchen clock. | Games read it to measure time. shocora computes it from your PC's clock so time passes at the right speed. | Like `QueryPerformanceCounter` or `clock_gettime`: a monotonic tick counter at a fixed rate. Timeouts, sleeps and frame timing all derive from it. | Read with `mftb` (TBL/TBU); shocora derives ticks from `Instant` scaled by the game speed so paused or double-speed time stays consistent. |
| <a id="t2-14"></a>2.14 | Decrementer | A countdown timer that [interrupts](#t4-27) the [CPU](#t2-1) when it reaches zero. | An egg timer. | The system uses it to switch between [threads](#t4-10) and fire [alarms](#t4-24). | The hardware timer that makes preemptive multitasking possible: when it fires, the OS [Scheduler](#t4-15) may switch [threads](#t4-10) ([Time slice](#t4-14)). | 32-bit, decremented at the time-base rate; raising its exception drives the [Cafe OS](#t4-2) [scheduler](#t4-15)'s preemption and [alarm](#t4-24) queue. shocora schedules by instruction count instead. |
| <a id="t2-15"></a>2.15 | GPU | The graphics chip. It turns 3D models and [textures](#t5-14) into the picture on screen. | A painter who paints a new picture many times per second. | Drawing is the second-hardest job for an [emulator](#t1-1). | Same role as your graphics card. Wii U games talk to it at a much lower level than DirectX/Vulkan games do ([GX2](#t5-1)). | Fixed-function plus unified VLIW5 [shader](#t2-17) [cores](#t2-3); command processor consumes [PM4](#t5-3) from indirect buffers. |
| <a id="t2-16"></a>2.16 | Latte | The Wii U's [GPU](#t2-15), designed by AMD (Radeon R700 family). It contains 32 MB of fast memory. | The console's painter. | shocora reads the painting orders Latte would receive and repaints them with your graphics card. | A Radeon HD 4000-era design. Unlike a PC GPU, its memory is shared with the [CPU](#t2-1), and games write its hardware commands directly ([Command buffer](#t5-2), [PM4](#t5-3)). | "GPU7", an RV7xx-class design at ~550 MHz; 32 MiB MEM1 [eDRAM](#t2-20) plus 3 MiB for Wii mode; [registers](#t2-9) follow the [R600](#t2-18)/R700 register reference. |
| <a id="t2-17"></a>2.17 | Shader | A small program that runs on the [GPU](#t2-15) to compute the position of each corner of a shape ([vertex shader](#t5-9)) or the colour of each pixel ([pixel shader](#t5-10)). | The painter's technique for one kind of brushstroke. | Wii U shaders are written in [Latte](#t2-16)'s own language. shocora translates each one for your graphics card. | On PC, games ship shaders as HLSL/GLSL or SPIR-V and the driver compiles them. Wii U games ship them already compiled for [Latte](#t2-16), so the emulator must decompile and recompile each one ([R600 / R700 ISA](#t2-18)). | Programs are CF (control flow) clauses calling ALU (VLIW5 x/y/z/w/t), TEX and VTX clauses; GPRs are vec4, plus constant files and kcache banks. |
| <a id="t2-18"></a>2.18 | R600 / R700 ISA | The language of [Latte](#t2-16)'s [shaders](#t2-17). | A painting style only that painter knows. | shocora converts it to WGSL, a modern [shader](#t2-17) language. | The GPU's machine code, very different from a CPU's: instructions grouped in clauses, each ALU instruction working on up to 5 values at once. shocora turns it into WGSL ([wgpu / Vulkan / DirectX 12](#t5-39)). | shocora decodes the binary (`core/gpu/src/shader`) into WGSL; predicates, PV/PS previous-result [registers](#t2-9) and loop/`ALU_PUSH_BEFORE` stacks must be modelled. |
| <a id="t2-19"></a>2.19 | VRAM | Memory used by the graphics chip. | The painter's canvas and paint storage. | On a PC, [textures](#t5-14) and images the [emulator](#t1-1) draws live in your graphics card's memory. | On the Wii U there is no separate VRAM besides [MEM1 (eDRAM)](#t2-20): textures live in main memory ([MEM2](#t2-21)). On your PC they are copied into VRAM, so the emulator keeps two copies in sync ([Texture](#t5-14)). | [wgpu](#t5-39) allocates device-local memory via gpu-allocator; host-visible staging for uploads is separate and counts toward the process's [working set](#t11-15). |
| <a id="t2-20"></a>2.20 | MEM1 (eDRAM) | 32 MB of very fast memory inside [Latte](#t2-16). | A small, ultra-fast workbench. | Games put the pictures they are drawing there. | A small, fast memory games use for the images they are drawing ([Render target / color buffer](#t5-17)), like a GPU's on-chip tile memory. For the emulator it is just part of the [Address space](#t3-2). | Physical `0x00000000`, effective `0xF4000000`, 32 MiB; [GX2](#t5-1) places [scan buffers](#t5-28) and hot [render targets](#t5-17) here; the [host](#t1-3) treats it like any other [guest](#t1-2) memory. |
| <a id="t2-21"></a>2.21 | MEM2 | The main memory: 2 GB, of which games can use about 1 GB. | The big pantry. | Holds the game's program, data and most [textures](#t5-14). shocora reserves the same space on your PC. | The RAM the game's [program](#t4-6), [heaps](#t3-6) and data live in. Only the pages the game actually touches cost host RAM ([Working set / memory usage](#t11-15)). | Games see 1 GiB at effective `0x10000000`; shocora commits it inside a 4 GiB [host](#t1-3) reservation, so only touched pages use RAM. |
| <a id="t2-22"></a>2.22 | Starbuck | A small ARM processor inside the console that handles security, storage, USB and Wi-Fi. | The building's security guard and mailroom. | shocora doesn't imitate this chip; it just provides the services the game asks for. | A separate computer inside the console running its own small OS, [IOSU](#t10-1). Games ask it for files and network through messages ([IPC](#t10-2)). | ARM926EJ-S running [IOSU](#t10-1), a microkernel with processes (FS, MCP, NET, USB, ACP, NIM…) serving `/dev/*` nodes over [IPC](#t10-2). |
| <a id="t2-23"></a>2.23 | NAND / MLC | The built-in flash storage (8 or 32 GB). | The console's hard drive. | Holds installed games, updates, [DLC](#t8-8) and saves. shocora uses a normal folder with the same layout ([`mlc01`](#t8-14), as in [Cemu](#t11-16)). | The equivalent of the console's SSD. Its folder layout is what the emulator recreates as `mlc01` ([`mlc01`](#t8-14)). | eMMC with an encrypted FAT-like file system ("FSA" view `/vol/storage_mlc01`); [titles](#t8-1) under `usr/title/<high>/<low>/`. |
| <a id="t2-24"></a>2.24 | SLC | A smaller flash chip for system files. | A locked drawer for the console's own papers. | Rarely needed by games. | The system's own drive, like a recovery partition. Games rarely read it. | 512 MiB [NAND](#t2-23) holding `sys/` [titles](#t8-1) ([OS](#t4-1), [HOME Menu](#t4-30)) and `config/`; mirrored as SLC/SLCCMPT. |
| <a id="t2-25"></a>2.25 | SEEPROM / OTP | Tiny chips holding the console's unique ID and secret keys. | The console's passport. | Not needed for decrypted games. | Where the console's encryption keys live. Encrypted game files ([NUS format](#t8-13)) need them; already-decrypted dumps don't. | OTP holds eFuse keys (common key, per-console keys); SEEPROM holds serial, board data and some keys; needed only to decrypt NUS/disc content. |

To a game it is just a second screen ([Scan buffer](#t5-28)) and an input device ([VPAD](#t7-1)). | Video is H.264-encoded on the console and streamed over 5 [GHz](#t2-4) Wi-Fi at 854×480 ≈ 60 Hz; input returns over the same link. |
| <a id="t2-27"></a>2.27 | DRC | The internal name of the [GamePad](#t2-26) ("Disc Remote Controller"). | The [GamePad](#t2-26)'s code name. | Appears in function names such as `GX2SetDRCBuffer`. | You will see it in function and file names; it always means the [GamePad](#t2-26). | [GX2](#t5-1) names: `GX2SetDRCBuffer`, `GX2_SCAN_TARGET_DRC`; [VPAD](#t7-1) channel 0; up to two DRCs at the system level. |
| <a id="t2-28"></a>2.28 | TV | The main screen, up to 1080p (most games draw at 720p). | The main stage. | The first picture shocora shows. | The ordinary HDMI output. Most games render at 1280×720 and the console scales up. | `GX2SetTVBuffer` modes 480p/720p/1080p (+ 1080i); scan-out via the display controller, double/triple buffered by [GX2](#t5-1). |
| <a id="t2-29"></a>2.29 | Pro Controller | A regular wireless controller. | An ordinary gamepad. | Another input option. | Read through a different library than the GamePad ([KPAD / WPAD (`padscore`)](#t7-2)). | Bluetooth HID extension `WPAD_EXT_PRO_CONTROLLER`, read through [KPAD](#t7-2)/WPAD with `KPADReadEx`. |

## 3. Memory and addresses

Memory is a very long row of numbered boxes, each holding one byte. A box's number is its **address**. Programs find their data by address.

| # | Term | In plain words | Picture it as | Why it matters | For intermediates | For experts |
| ---: | --- | --- | --- | --- | --- | --- |
| <a id="t3-1"></a>3.1 | Address | The number of a memory location. | A house number on a very long street. | Every pointer in the game is an address. | The same as a pointer value in C. In the guest, pointers are 32-bit, so everything fits in 4 GB. | 32-bit [effective addresses](#t3-3); [Cafe OS](#t4-2) uses fixed BAT/page-table mappings per process, so games never change translation. |
| <a id="t3-2"></a>3.2 | Address space | All [addresses](#t3-1) a program can use. The Wii U [CPU](#t2-1) uses 32-bit addresses, so 4 GB of them. | The whole street, even where no houses are built yet. | shocora reserves one 4 GB block on your PC, so "[guest](#t1-2) [address](#t3-1) X" is simply "start of block + X". That makes memory access fast. | Like a process's virtual memory: shocora reserves one 4 GB virtual block, so guest address X is simply `base + X` in the host, and the [JIT (just-in-time compiler) / recompiler](#t11-2) can access guest memory with one instruction. | `AddressSpace` reserves 4 GiB (`VirtualAlloc(MEM_RESERVE)` / `mmap(PROT_NONE)`) and commits regions on mapping; the [JIT](#t11-2) accesses `base + ea` without bounds checks. |
| <a id="t3-3"></a>3.3 | Effective address | An [address](#t3-1) as the game's code sees it. | The street address on an envelope. | What the [CPU](#t2-1) uses. | The address the game's code uses ([Address](#t3-1)). On the Wii U it differs from the [Physical address](#t3-4) only by fixed offsets. | What every load/store, branch target and pointer in [guest](#t1-2) data uses. |
| <a id="t3-4"></a>3.4 | Physical address | An [address](#t3-1) as the hardware ([GPU](#t2-15), disk transfers) sees it. | The GPS coordinates of the same house. | The [GPU](#t2-15)'s orders contain physical [addresses](#t3-1); shocora converts them back. | The GPU and DMA engines bypass the CPU's address translation, so [command buffers](#t5-2) contain physical addresses that the emulator converts back to [effective](#t3-3) ones. | [PM4](#t5-3) packets and [GX2](#t5-1) [registers](#t2-9) carry physical [addresses](#t3-1); `wiiu_mem_addr::effective_to_physical`/inverse map [MEM1](#t2-20), [MEM2](#t2-21) and the foreground area. |
| <a id="t3-5"></a>3.5 | Code area | Where the game's program is loaded (starting at `0x02000000`). | The shelf where the recipe book sits. | If a game rewrites its own code, shocora must throw away translations of that code. | Where the [RPX](#t4-6) is loaded. If the game writes there (rare), translated code for that area must be thrown away ([Code cache](#t11-6)). | [RPX](#t4-6) `.text` loads at `0x02000000`, data at `0x10000000`; `ICInvalidateRange` or writes there invalidate [JIT](#t11-2) entries in the overlapping range. |
| <a id="t3-6"></a>3.6 | Heap | A pool of memory the game hands out piece by piece as it needs it. | A shared pantry where you take containers as needed. | The Wii U system offers several kinds (expanding, frame, unit heaps); shocora implements them. | Like `malloc`, but the game picks between several allocator styles. They manage memory inside the guest's [MEM2](#t2-21), not host memory. | `MEMExpHeap` (free list, best/first fit, both ends), `MEMFrmHeap` (push/pop states), `MEMUnitHeap` (fixed blocks); default heap via `MEMGetBaseHeapHandle` and `MEMAllocFromDefaultHeapEx`. |
| <a id="t3-7"></a>3.7 | Foreground bucket | Memory reserved for the app on screen, taken back when it goes to the background. | A table at a restaurant you keep only while you're seated. | Some games use it for screenshots and temporary data. | Memory that belongs to whichever app is on screen; games must give it back when they go to the background ([`proc_ui`](#t4-29)). | `OSGetForegroundBucket` / `OSGetForegroundBucketFreeArea`; ProcUI asks the app to save it before releasing the foreground. |
| <a id="t3-8"></a>3.8 | Cache line | The 32-byte chunk the [CPU](#t2-1) [cache](#t2-5) works in. | The size of one scoop. | The game's "flush this range" requests come in [cache](#t2-5) lines, and they tell shocora which memory the [GPU](#t2-15) should re-read. | The smallest unit the [Cache](#t2-5) reads or writes, 32 bytes here (64 on most PCs). Cache-flush calls work in these units. | 32 bytes; `dcbz` zeroes one, `DCFlushRange` rounds to them. shocora's `WriteTracker` stamps 4 KiB pages so the [GPU](#t2-15) re-hashes only what changed. |
| <a id="t3-9"></a>3.9 | Aperture | A window that shows a [GPU](#t2-15) image in simple row-by-row order. | A window that rearranges a jigsaw puzzle into a flat picture as you look through it. | A few games read rendered pictures through it. | Lets the CPU read a [tiled](#t5-21) image as if it were a plain array of pixels. Rarely used, but the emulator must support it. | `GX2AllocateTilingApertureEx` programs a hardware window that detiles on access; shocora must serve linear views of tiled [surfaces](#t5-16). |

## 4. The operating system (Cafe OS)

A game doesn't talk to the hardware directly for most things. It calls ready-made functions in the console's **operating system** (Cafe OS): "start a thread", "allocate memory", "open a file". shocora rewrites those functions itself instead of running Nintendo's code.

| # | Term | In plain words | Picture it as | Why it matters | For intermediates | For experts |
| ---: | --- | --- | --- | --- | --- | --- |
| <a id="t4-1"></a>4.1 | Operating system (OS) | The base software that manages the hardware and offers services to programs. | The building management: electricity, water, mail, keys. | Games depend on it for nearly everything. | The same role as Windows or Linux: [threads](#t4-10), memory, files, timers. But it is small, and games link to it like a library ([Library](#t4-5)). | [Cafe OS](#t4-2): a [PowerPC](#t2-7) kernel plus [RPL](#t4-7) libraries in user space; multi-process (game, [HOME Menu](#t4-30), overlays) with per-process [address spaces](#t3-2). |
| <a id="t4-2"></a>4.2 | Cafe OS | The Wii U's [operating system](#t4-1) ("Cafe" was the console's code name). | The Wii U's building management. | shocora reimplements it in Rust. | Games never see the kernel directly; they call functions exported by system [RPLs](#t4-7), mostly [`coreinit`](#t4-9). | Kernel handles scheduling, [IPC](#t10-2) to [IOSU](#t10-1) and memory; `coreinit.rpl` wraps it with the user-visible API (~2,000 [exports](#t4-8)). |
| <a id="t4-3"></a>4.3 | HLE (high-level emulation) | Replacing a system function with your own code that gives the same result, instead of imitating the hardware underneath. | Hiring a new receptionist who gives the same answers, rather than rebuilding the old phone switchboard. | How shocora (and [Cemu](#t11-16)) provide the Wii U's system. Faster, and needs no files from a real console. | Like Wine on Linux, which reimplements the Windows API instead of running Windows: each OS function the game imports ([Import / export](#t4-8)) is replaced by Rust code doing the same thing. | Each imported symbol is bound to a stub that traps into `wiiu_cafe_os::dispatch` (`StepEvent::HleCall(index)`); the `hle_export` macro generates argument marshalling from the [PowerPC](#t2-7) ABI (r3–r10, f1–f8). |
| <a id="t4-4"></a>4.4 | LLE (low-level emulation) | Imitating the actual hardware so the original system software can run. | Rebuilding the switchboard wire by wire. | More exact but much slower. Not used by shocora. | Like running the real Windows inside a virtual machine: exact, but you must emulate every hardware detail and need the console's firmware. | Would require emulating the kernel, MMU, [interrupts](#t4-27) and [IOSU](#t10-1) on [Starbuck](#t2-22), plus a [NAND](#t2-23) dump with keys. |
| <a id="t4-5"></a>4.5 | Library | A collection of ready-made functions a program can call. | A toolbox. | The Wii U's system comes as libraries such as [`coreinit`](#t4-9), `gx2`, `snd_core`. | Like a DLL or `.so` file. The Wii U format is [RPL](#t4-7). | [RPLs](#t4-7) [export](#t4-8) functions and data; resolution happens at load via import sections, or at run time via `OSDynLoad_FindExport`. |
| <a id="t4-6"></a>4.6 | RPX | The game's main program file. | The game's main recipe book. | The first thing shocora loads (`code/*.rpx`). | The game's `.exe`: an ELF file (the Linux executable format) with Nintendo extensions such as compressed sections. | ELF32 [big-endian](#t2-8), `EI_OSABI` 0xCA/0xFE, sections zlib-compressed (`SHF_RPL_ZLIB`), `RPL_FILEINFO` with sizes for text/data/load areas. |
| <a id="t4-7"></a>4.7 | RPL | A [library](#t4-5) file in the same format as [RPX](#t4-6). | An extra recipe booklet. | System libraries are replaced by shocora's own versions; libraries that ship with a game are loaded normally. | The Wii U's DLL. When a game imports from `coreinit.rpl`, shocora provides its own version instead of loading a file ([HLE (high-level emulation)](#t4-3)). | Same container; `.fexports`/`.dexports` sections list [exports](#t4-8) with name hashes; relocations are `R_PPC_*` (ADDR16_HA/LO, REL24, …). |
| <a id="t4-8"></a>4.8 | Import / export | The functions a file needs from others (imports) and offers to others (exports). | A shopping list and a menu. | shocora connects each import to the right function when loading. | Like the import table of a Windows `.exe`: the list of DLL functions it needs, filled in by the loader at start-up. | Imports live in `.fimports_<lib>`/`.dimports_<lib>` sections; relocations against them are resolved by the loader (`core/rpl`). |
| <a id="t4-9"></a>4.9 | `coreinit` | The [core](#t2-3) system [library](#t4-5): [threads](#t4-10), memory, time, files. | The building's main office. | The [library](#t4-5) games call most. | The Wii U's kernel32.dll / libc combined: threads, [locks](#t4-17), [heaps](#t3-6), time, files. | [Threads](#t4-10), sync [primitives](#t5-6), [alarms](#t4-24), [heaps](#t3-6), [cache](#t2-5) ops, `OSReport`, FS client, [`OSDynLoad`](#t4-31), MP (multi-process) and system info all live here. |
| <a id="t4-10"></a>4.10 | Thread | One sequence of work inside a program. A game runs dozens at once (rendering, sound, loading, physics…). | One worker with one task list. | shocora decides which thread runs on which [core](#t2-3) and when, like the real system. | The same as threads in your programs (`std::thread`, `pthread`). On the Wii U each thread is pinned to a [Core](#t2-3) ([Affinity](#t4-13)) and switched by the [Scheduler](#t4-15). | Preemptive, priority-based; a thread runs on one [core](#t2-3) at a time. BotW runs ~50 threads, many blocked on [message queues](#t4-23). |
| <a id="t4-11"></a>4.11 | OSThread | The Wii U's description of a [thread](#t4-10): its saved [registers](#t2-9), stack, [priority](#t4-12) and allowed [cores](#t2-3). | A worker's ID card and notes. | shocora keeps one for every game [thread](#t4-10). | The thread object, like a `pthread_t` but a structure in guest memory the game allocates itself. It holds the saved [registers](#t2-9) used for a [Context switch](#t4-16). | 0x6A0-byte [guest](#t1-2) struct (context at +0, state, [priority](#t4-12), [affinity](#t4-13), stack, [TLS](#t4-26)…); shocora mirrors scheduling state in a [host](#t1-3) `ThreadRecord`. |
| <a id="t4-12"></a>4.12 | Priority | How important a [thread](#t4-10) is (0 = most important, 31 = least). | A queue where VIPs go first. | The most important ready [thread](#t4-10) always gets the [core](#t2-3). | Like thread priorities in Windows, but strict: a ready higher-priority thread always runs first, so a busy one can starve lower ones. | Effective priority plus boost for [mutex](#t4-17) owners; `OSSetThreadPriority`. Ties are round-robin by last run. |
| <a id="t4-13"></a>4.13 | Affinity | Which [cores](#t2-3) a [thread](#t4-10) is allowed to run on. | A worker who may only work in one kitchen. | Most game [threads](#t4-10) stay on one [core](#t2-3). | Like `SetThreadAffinityMask`. Most game threads are pinned to one core, so the emulator can run each guest core on its own host thread ([Multi-core mode](#t11-7)). | `OS_THREAD_ATTRIB_AFFINITY_CPU0/1/2` bits in the [thread](#t4-10) attributes; `OSSetThreadAffinity`. Side by side, a [core](#t2-3) runs only threads of its own. |
| <a id="t4-14"></a>4.14 | Time slice | How long a [thread](#t4-10) may run before others of the same [priority](#t4-12) get a turn. | Taking turns on a swing. | shocora measures it in game instructions. | The fairness rule: when time is up, the [Scheduler](#t4-15) lets another thread of the same [Priority](#t4-12) run. | [Cafe OS](#t4-2) uses the [decrementer](#t2-14); shocora uses `TIME_SLICE` = 100,000 [guest](#t1-2) instructions, then reschedules with `Reschedule::Yield`. |
| <a id="t4-15"></a>4.15 | Scheduler | The part of the [OS](#t4-1) that picks which [thread](#t4-10) runs next. | The shift manager. | A slow scheduler means wasted time on every switch. | The OS component that picks the next thread. shocora's is reimplemented in Rust and is called on every blocking call, so its speed matters. | shocora's `Scheduler` scans a `BTreeMap` of [threads](#t4-10) and evaluates wait conditions ([mutex](#t4-17) free, queue non-empty, deadline…) directly against [guest](#t1-2) memory. |
| <a id="t4-16"></a>4.16 | Context switch | Saving one [thread](#t4-10)'s [registers](#t2-9) and loading another's so a [core](#t2-3) can change jobs. | A cook putting one dish aside and picking up another. | Happens thousands of times per second, so it must be cheap. | Saving one thread's [registers](#t2-9) and loading another's. In shocora this is copying a structure, so it must not allocate memory. | Saves GPRs/FPRs/CR/LR/CTR/XER/FPSCR/[GQRs](#t2-11); `OSSwitchFiberEx` and [callbacks](#t4-28) do the same at a smaller scale. |
| <a id="t4-17"></a>4.17 | Mutex (OSMutex, OSFastMutex) | A lock that lets only one [thread](#t4-10) at a time touch some shared data. | The single key to a bathroom. | Breath of the Wild locks and unlocks millions of times per second. If shocora handles this slowly, the whole game slows. | The same as `std::mutex`. Games lock and unlock extremely often, almost always without anyone waiting, so the uncontended path must be very cheap ([Contention](#t4-18), [Fast call](#t11-11)). | `OSMutex` is recursive with owner/count and [priority](#t4-12) inheritance; `OSFastMutex` spins on an atomic first. shocora keeps ownership in a [host](#t1-3) map and only scans waiters when a lock was ever contended. |
| <a id="t4-18"></a>4.18 | Contention | When a [thread](#t4-10) wants a lock someone else holds and has to wait. | A queue outside the bathroom. | Waiting [threads](#t4-10) must be woken when the lock frees up. | When it happens, the waiting thread blocks and the [Scheduler](#t4-15) runs something else until the [Mutex (OSMutex, OSFastMutex)](#t4-17) is released. | A contended acquire blocks with `Wait::Mutex(key)`; a release requests a [priority](#t4-12) reschedule so an equal-core waiter can run. |
| <a id="t4-19"></a>4.19 | Spinlock | A lock where the waiting [thread](#t4-10) keeps checking instead of sleeping. | Rattling the door handle until it opens. | For very short waits. shocora treats it like a [mutex](#t4-17). | Like a busy-wait loop on an atomic flag. On real hardware it avoids a [Context switch](#t4-16); in an emulator it is simpler to treat it as a [Mutex (OSMutex, OSFastMutex)](#t4-17). | `OSUninterruptibleSpinLock_Acquire` also disables [interrupts](#t4-27) on the console; the [HLE](#t4-3) has no interrupts to mask. |
| <a id="t4-20"></a>4.20 | Condition variable (OSCondition) | Lets a [thread](#t4-10) sleep until another thread says "something changed". | "Wake me up when the pizza arrives." | Used for queues between game [threads](#t4-10). | The same as `std::condition_variable`: wait while releasing a [Mutex (OSMutex, OSFastMutex)](#t4-17), wake on a signal. | `OSWaitCond` atomically releases the [mutex](#t4-17) (keeping its recursion count) and reacquires it after `OSSignalCond`. |
| <a id="t4-21"></a>4.21 | Event (OSEvent) | A flag a [thread](#t4-10) can wait for. | A doorbell. | "Frame finished", "file loaded" and similar signals. | Like a Windows event object (`CreateEvent`): set it, and waiting threads wake. | [Guest](#t1-2) struct with magic "eVnT", state at +0x0C and mode at +0x20 (auto-reset clears on a successful wait); `OSWaitEventWithTimeout` too. |
| <a id="t4-22"></a>4.22 | Semaphore (OSSemaphore) | A counter of available tickets; a [thread](#t4-10) waits when none are left. | A car park that shows how many spaces are free. | Limits how many [threads](#t4-10) use something at once. | Same as the classic counting semaphore in any threading library. | Magic "sMPH", count at +0x0C; `OSWaitSemaphore` decrements or blocks, `OSSignalSemaphore` increments. |
| <a id="t4-23"></a>4.23 | Message queue (OSMessageQueue) | A mailbox where [threads](#t4-10) leave messages for each other. | A pigeonhole for notes. | [Threads](#t4-10) hand work to each other this way. The system also sends app messages through it. | Like a bounded channel (Go channel, `mpsc::sync_channel`): fixed-size messages, blocking when empty or full. | Ring of 16-byte `OSMessage`s; count at +0x30, used at +0x38; `OS_MESSAGE_FLAGS_BLOCKING` decides whether send/receive block. The system app queue carries ProcUI messages. |
| <a id="t4-24"></a>4.24 | Alarm (OSAlarm) | A function that runs at a set time, once or repeatedly. | An alarm clock. | Timers and regular jobs. | Like a timer callback (`setTimeout`/`setInterval`). It runs from the timer [Interrupt](#t4-27), not from a normal thread, so it must not block. | Per-core alarm queues; `OSSetAlarm`, `OSSetPeriodicAlarm`; handlers run in [interrupt](#t4-27) context, so they must not block. shocora fires them on the [callback](#t4-28) [core](#t2-3) between slices. |
| <a id="t4-25"></a>4.25 | Rendezvous | A meeting point where several [cores](#t2-3) wait until all have arrived. | Waiting at the gate until the whole group is there. | Used when the game starts up. | A barrier (`std::barrier`) for whole [cores](#t2-3). | `OSWaitRendezvous(rv, coreMask)` waits until each [core](#t2-3) in the mask has written its slot. |
| <a id="t4-26"></a>4.26 | Thread-local storage (TLS) / thread-specific data | Data each [thread](#t4-10) has its own copy of. | Each worker's personal locker. | Game engines keep per-thread information here. shocora lets each [core](#t2-3) read it without asking the shared [OS](#t4-1), which saves a lot of waiting. | The same as `thread_local` in C++/Rust. The engine looks it up many times per frame, which is why shocora made it lock-free ([Fast call](#t11-11)). | `__tls_get_addr(tls_index{module, offset})` returns the [thread](#t4-10)'s block plus offset, allocating a copy of the TLS image on first use; `OSSetThreadSpecific` has 16 slots. shocora keeps both in `CpuState`, so they are lock-free [fast calls](#t11-11). |
| <a id="t4-27"></a>4.27 | Interrupt | A hardware signal that makes the [CPU](#t2-1) stop and handle something urgent. | A phone ringing while you cook. | The screen refresh and "[GPU](#t2-15) finished" events arrive this way. | Like a hardware signal handler: the CPU stops what it is doing to run OS code. The emulator delivers the same events as [callbacks](#t4-28). | Sources: [decrementer](#t2-14), [IPC](#t10-2), [GPU](#t2-15) (EOP, [vsync](#t5-30), flip), DMA; delivered via the PI interrupt controller to kernel handlers. |
| <a id="t4-28"></a>4.28 | Callback | A function the game gives the system, to be called later when something happens. | Leaving your number: "call me when it's ready". | shocora calls them at the right moments, for example when a frame is shown. | The same idea as a callback function you pass to a library, except it is guest code the emulator must run on a guest [Core](#t2-3). | shocora runs [guest](#t1-2) callbacks (`GuestCall`) on a borrowed [core](#t2-3) with a return trampoline, after saving and before restoring the interrupted context. |
| <a id="t4-29"></a>4.29 | `proc_ui` | The [library](#t4-5) that tells a game whether it is on screen, in the background or closing. | The stage manager saying "you're on" or "take a break". | shocora always says "you're on screen". | Like the app lifecycle on a phone (foreground/background events). Games poll it every frame. | `ProcUIProcessMessages` returns `PROCUI_STATUS_IN_FOREGROUND` / `_RELEASE_FOREGROUND` / `_EXITING`; release [callbacks](#t4-28) must free [GPU](#t2-15) and foreground memory. |
| <a id="t4-30"></a>4.30 | HOME Menu | The overlay that pauses the game when you press HOME. | An intermission. | Not imitated. | A separate app that takes over the screen; the game must release its graphics memory first ([`proc_ui`](#t4-29), [Foreground bucket](#t3-7)). | A separate process that takes the foreground; the game releases [GX2](#t5-1) resources, then reacquires them on return. |
| <a id="t4-31"></a>4.31 | `OSDynLoad` | Loading a [library](#t4-5) while the game is running. | Fetching an extra manual from the shelf mid-task. | shocora answers with its own functions. | Like `LoadLibrary` + `GetProcAddress` / `dlopen` + `dlsym`. | `OSDynLoad_Acquire`, `OSDynLoad_FindExport`, `OSDynLoad_Release`; also used by the system to resolve `*.rpl` [imports](#t4-8). |
| <a id="t4-32"></a>4.32 | `__ghsLock` | The lock protecting the C standard [library](#t4-5) inside the game (memory allocation, text output). | The key to the shared supply cupboard. | Another very frequently used lock. | A [Mutex (OSMutex, OSFastMutex)](#t4-17) inside the game's C library; one of the most frequently taken locks. | Green Hills MULTI runtime hooks (`__ghsLock`/`__ghsUnlock`) protecting malloc and stdio; recursive per [thread](#t4-10). |

## 5. Graphics (GX2 and Latte)

To draw a frame, a game doesn't paint pixels itself. It sends a long list of orders to the GPU: "use this texture", "use this shader", "draw these triangles". GX2 is the Wii U library for writing those orders.

| # | Term | In plain words | Picture it as | Why it matters | For intermediates | For experts |
| ---: | --- | --- | --- | --- | --- | --- |
| <a id="t5-1"></a>5.1 | GX2 | The Wii U's graphics [library](#t4-5). | The order form you fill in for the painter. | Games call GX2; shocora turns the result into drawings on your graphics card. | Like a very thin OpenGL that writes the GPU's own commands ([PM4](#t5-3)) into memory instead of calling a driver. There is no driver doing validation or state tracking for the game. | Thin user-mode driver: GX2 functions write [PM4](#t5-3) directly into a [command buffer](#t5-2); `GX2Flush` submits it through the kernel's TCL to the command processor. |
| <a id="t5-2"></a>5.2 | Command buffer | A block of memory filled with drawing orders, handed to the [GPU](#t2-15) in one go. | A stack of filled-in order forms. | shocora works through these on a separate "[GPU thread](#t11-8)", as [Cemu](#t11-16) does, so the [CPU](#t2-1) side doesn't wait. | Like a Vulkan command buffer, but at the hardware level: once submitted, the GPU executes it while the CPU continues. shocora executes them on the [GPU thread](#t11-8). | Submitted as indirect buffers (IB) to the ring; shocora's `Gpu::threaded` executes submissions in order on its [GPU thread](#t11-8) and retires [timestamps](#t5-32). |
| <a id="t5-3"></a>5.3 | PM4 | The format of each order in the [command buffer](#t5-2). | The layout of the order form. | shocora's command processor reads PM4 packets one by one. | The binary encoding of those commands: a header saying "set these registers" or "draw", followed by data. The emulator parses them like a network protocol. | Type-3 packets: header `(3<<30) \| (count-1)<<16 \| opcode<<8`; e.g. `SET_CONTEXT_REG`, `DRAW_INDEX_AUTO`, `INDIRECT_BUFFER_PRIV`, `EVENT_WRITE_EOP`, `MEM_WRITE`, `WAIT_REG_MEM`, `SURFACE_SYNC`. |
| <a id="t5-4"></a>5.4 | Display list | A recorded set of orders the game can replay many times. | A saved shopping list you reuse every week. | Saves the game work for things that don't change. | Like a pre-recorded Vulkan secondary command buffer that can be replayed. | `GX2BeginDisplayList`/`GX2EndDisplayList` record into a user buffer; `GX2CallDisplayList` emits an `INDIRECT_BUFFER_PRIV` to it. |
| <a id="t5-5"></a>5.5 | Draw call | One order to draw a batch of shapes. | One brushstroke instruction. | A Breath of the Wild frame has about 1,000–2,000. Each costs time on your PC too. | Same as a draw call in DirectX/Vulkan. The difference: the game sets GPU registers directly, so the emulator must work out the matching [Pipeline](#t5-37) for every draw. | `DRAW_INDEX_AUTO`, `DRAW_INDEX_2`, `DRAW_INDEX_IMMD`; state is whatever the context [registers](#t2-9) hold at that moment, so shocora hashes state into a [pipeline](#t5-37) key per draw. |
| <a id="t5-6"></a>5.6 | Primitive | A basic shape: point, line, triangle, strip of triangles, quad. | A puzzle piece. | Everything 3D is made of triangles. PC graphics cards can't draw quads, so shocora splits them into triangles. | The same shape types as in any graphics API, plus quads and rectangles that modern APIs dropped. | `VGT_PRIMITIVE_TYPE`: lists/strips/fans, `QUADLIST`, `QUADSTRIP`, `RECTLIST` (3 vertices → screen-aligned rectangle), `LINELOOP`; non-native ones are expanded into index lists. |
| <a id="t5-7"></a>5.7 | Vertex | A corner point of a shape, with position, colour, [texture](#t5-14) coordinates and so on. | A pin in a pin-and-string picture. | Read by the [vertex shader](#t5-9). | Same as in any 3D engine; the [Fetch shader](#t5-8) describes its layout in memory. | Fetched through `SQ_VTX_CONSTANT` resources ([address](#t3-1), stride, size); index buffers in u16/u32, little- or [big-endian](#t2-8) per `VGT_DMA_SWAP`. |
| <a id="t5-8"></a>5.8 | Fetch shader | A tiny program describing how [vertex](#t5-7) data is laid out in memory. | The legend explaining a spreadsheet's columns. | shocora reads it to know how to feed vertices to your graphics card. | The Wii U's version of a vertex input layout (`D3D12_INPUT_ELEMENT_DESC`, `VkVertexInputAttributeDescription`), except that it is GPU code instead of a description. | A separate CF program of `VTX_FETCH` instructions called with `CALL_FS`; each fetch names a buffer, offset, data format and destination [swizzle](#t5-23). |
| <a id="t5-9"></a>5.9 | Vertex shader | Computes where each [vertex](#t5-7) ends up on screen. | Moving the pins into place. | Translated by shocora. | Same as in DirectX/OpenGL, but stored as [Latte](#t2-16) machine code ([R600 / R700 ISA](#t2-18)). | [Exports](#t4-8) position (`EXP POS`) and parameters (`EXP PARAM0..`); `SPI_VS_OUT_CONFIG`/`SPI_PS_INPUT_CNTL` link VS outputs to PS inputs. |
| <a id="t5-10"></a>5.10 | Pixel shader | Computes the colour of each pixel of a shape. | Colouring in between the pins. | Translated by shocora. | Same as a fragment shader in DirectX/OpenGL, also stored as machine code ([R600 / R700 ISA](#t2-18)). | [Exports](#t4-8) to up to 8 color targets (`CB_SHADER_MASK`) and depth; `KILL` instructions, alpha test (`SX_ALPHA_TEST_CONTROL`) and `PIX_CENTER` conventions must be matched. |
| <a id="t5-11"></a>5.11 | Geometry shader | Creates or removes shapes between the two stages above. | An assistant who adds or erases pins. | Rare on Wii U; needs special handling on modern APIs. | Same as in DirectX 10+/OpenGL 3.2+; WebGPU, which shocora uses ([wgpu / Vulkan / DirectX 12](#t5-39)), has none. | R7xx GS reads from the ESGS ring and writes to the GSVS ring, followed by a copy [shader](#t2-17); WebGPU has no GS, so it must be emulated (e.g. in compute). |
| <a id="t5-12"></a>5.12 | Uniform | A value shared by all vertices or pixels of a draw (a matrix, a colour, a light). | Settings written at the top of the order form. | Sent with almost every [draw call](#t5-5). | Same as constant buffers / uniform buffers. The Wii U also has a register mode where constants are written one by one, which costs one call each. | [Register](#t2-9) mode: 256 vec4 ALU constants per stage (`GX2SetVertexUniformReg`); block mode: up to 16 constant buffers (`GX2SetVertexUniformBlock`). shocora stores used blocks in its arena per draw. |
| <a id="t5-13"></a>5.13 | Stream-out | Saving the [vertex shader](#t5-9)'s results to memory instead of drawing them. | Writing measurements down instead of building. | Used for particles and animation. | Same as transform feedback in OpenGL or stream output in DirectX 10. | `VGT_STRMOUT_*`, up to 4 buffers with offsets written back to memory; `GX2SetStreamOutBuffer`, `GX2SetStreamOutEnable`. shocora writes to a storage buffer from the [vertex](#t5-7) stage. |
| <a id="t5-14"></a>5.14 | Texture | An image wrapped onto shapes. | Wallpaper or a sticker. | Uploaded from game memory to your graphics card. Uploading them efficiently was a big speed-up for shocora. | Same as in any game. On the Wii U it lives in main memory ([MEM2](#t2-21)), so the emulator must notice when the game changes it and upload it again ([`GX2Invalidate`](#t5-34)). | `SQ_TEX_RESOURCE` (7 dwords: dim, tile mode, pitch, size, format, [swizzle](#t5-23), base/mip [addresses](#t3-1)) plus `SQ_TEX_SAMPLER`; shocora [caches](#t2-5) by `SurfaceKey` and content hash. |
| <a id="t5-15"></a>5.15 | Mipmap | Smaller copies of a [texture](#t5-14) for things far away. | Thumbnails of a photo. | Faster and smoother distant objects. | Same as mipmaps on PC. | Level 0 at `image`, levels ≥1 packed at `mipmaps` with `mipLevelOffset[]`; small levels degrade from 2D to 1D [tiling](#t5-21). |
| <a id="t5-16"></a>5.16 | Surface | Any image in [GPU](#t2-15) memory: a [texture](#t5-14), a picture being drawn, a depth image. | A canvas. | shocora keeps a matching canvas on your graphics card for each. | The general word for textures and render targets alike: an image with a size, [Format](#t5-19), [mip levels](#t5-15) and [tiling](#t5-21) mode. | `GX2Surface`: dim, width, height, depth, mipLevels, format, aa, use, imageSize, image, mipSize, [mipmaps](#t5-15), tileMode, [swizzle](#t5-23), alignment, pitch, mipLevelOffset[13]. |
| <a id="t5-17"></a>5.17 | Render target / color buffer | The image a draw paints into. | The canvas on the easel. | Games draw many intermediate images per frame (shadows, reflections, blur). | Same as a render target / framebuffer attachment. Games draw many per frame for effects; the emulator keeps them on the host GPU. | `CB_COLOR{n}_BASE/SIZE/VIEW/INFO`; slices and mips are selected by `viewMip`/`viewFirstSlice`. Targets that only the [host](#t1-3) has are tracked so they are never re-uploaded from stale [guest](#t1-2) memory. |
| <a id="t5-18"></a>5.18 | Depth buffer | An image storing how far away each pixel is. | A height map of the scene. | Hides what is behind other things. Also used for shadows. | Same as a depth/stencil buffer (Z-buffer). | `DB_DEPTH_BASE/SIZE/INFO`, HiZ/HTILE; formats D16, D24S8, D32F, D32F_S8X24. Sampled depth must keep 32-bit float precision. |
| <a id="t5-19"></a>5.19 | Format | How each pixel is stored: how many bits per colour, compressed or not. | The paint type: oil, watercolour… | shocora maps each Wii U format to one your graphics card understands. | Same as `DXGI_FORMAT_*` / `VkFormat`, with a few Wii U-only formats that must be converted. | `GX2SurfaceFormat` = hardware format \| type flags (UNORM 0x000, UINT 0x100, SNORM 0x200, SINT 0x300, SRGB 0x400, FLOAT 0x800); some formats need widening (e.g. 3-component) on the [host](#t1-3). |
| <a id="t5-20"></a>5.20 | BC1–BC5 | Compressed [texture](#t5-14) formats (also called DXT). | Vacuum-packed clothes. | Most game [textures](#t5-14) use them; PC graphics cards understand them directly. | The same DXT/BC compression PC games use, so no decompression is needed, only [untiling](#t5-21). | 4×4-texel blocks: 8 bytes (BC1, BC4) or 16 bytes (BC2, BC3, BC5); [tiling](#t5-21) operates on blocks, not texels. |
| <a id="t5-21"></a>5.21 | Tiling | Storing an image in small squares instead of row by row, so the [GPU](#t2-15) reads it faster. | Floor tiles instead of one long roll of carpet. | shocora has to "untile" [textures](#t5-14) before giving them to your graphics card. | PC GPUs do the same internally, but hide it. On the Wii U, games see the tiled layout in memory, so the emulator must convert ([AddrLib](#t5-25)). | Modes `LINEAR_GENERAL/ALIGNED`, `1D_TILED_THIN1/THICK`, `2D_TILED_THIN1–4/THICK`, `2B/3D/3B` variants; [Latte](#t2-16) has 2 pipes and 4 banks. |
| <a id="t5-22"></a>5.22 | Micro tile / macro tile | Small 8×8 tiles, and big tiles made of them spread across memory. | Tiles, and the rooms tiled with them. | Needed to find where each pixel is. | Two levels of [Tiling](#t5-21): small tiles for cache efficiency, big tiles to spread work over memory banks. | Micro tile: 8×8 elements, thin (1 slice) or thick (4 slices), with element bit-interleaving; macro tile: micro tiles distributed across pipes and banks. |
| <a id="t5-23"></a>5.23 | Swizzle | Extra [address](#t3-1) bits that shift where tiles start. | A different starting tile in each room. | Part of how shocora recognises the same image again. | A per-image shift of the [tile](#t5-22) pattern so that different images don't hit the same memory banks. | Bank/pipe swizzle in `surface.swizzle` bits 8–10 rotates the starting bank/pipe; masked when identifying a [surface](#t5-16) by [address](#t3-1) (`address & !0x7FF`). |
| <a id="t5-24"></a>5.24 | Pitch | The width of an image in memory, rounded up to fit tiles. | A shelf that is a little wider than the books. | Needed for [address](#t3-1) maths. | Same as "row pitch" / stride in DirectX: the memory width of one row, which can be larger than the image width. | In elements, aligned to the macro-tile width for 2D modes; bytes per row = pitch × bytes per element (or per block). |
| <a id="t5-25"></a>5.25 | AddrLib | AMD's code for calculating tiled image sizes and [addresses](#t3-1). | The tiler's rule book. | Ported into shocora. | The rule book for [tiled](#t5-21) layouts; used to find where every pixel is. | Port of AMD's addrlib ([R600](#t2-18)/R800 paths): `ComputeSurfaceInfo`, `ComputeSurfaceAddrFromCoord`; must match [GX2](#t5-1)'s sizes byte for byte. |
| <a id="t5-26"></a>5.26 | Anti-aliasing (MSAA) | Smoothing jagged edges by sampling each pixel several times. | Blurring the edge of a paper cut-out. | A few games use it. | Same MSAA you know from game settings. | Up to 8× (`GX2_AA_MODE`); CMASK/FMASK compression; resolved with `GX2ResolveAAColorBuffer`. |
| <a id="t5-27"></a>5.27 | Resolve / copy | Copying one image into another, sometimes changing its format. | Tracing a picture onto new paper. | Post-processing effects copy images a lot. shocora does it on your graphics card. | Same as `CopyResource`/`vkCmdCopyImage` and MSAA resolve. | `GX2CopySurface`, `GX2CopySurfaceEx`, depth→color copies, `GX2ResolveAAColorBuffer`; shocora performs them as [host](#t1-3) [texture](#t5-14) copies or draws, keeping data on the [GPU](#t2-15). |
| <a id="t5-28"></a>5.28 | Scan buffer | The finished picture sent to the [TV](#t2-28) or [GamePad](#t2-26). | The framed painting on the wall. | What you see in shocora's window. | The front buffer of a swap chain. | Allocated by the game in the [foreground bucket](#t3-7) and registered with `GX2SetTVBuffer`/`GX2SetDRCBuffer`; filled by `GX2CopyColorBufferToScanBuffer`. |
| <a id="t5-29"></a>5.29 | Swap / flip | Replacing the shown picture with the newly finished one. | Turning a page in a flip book. | One flip = one frame. shocora's [FPS](#t1-5) counts flips. | Same as `Present()` in DirectX or `vkQueuePresentKHR`. | `GX2SwapScanBuffers` queues a flip executed by the [GPU](#t2-15) at the next eligible [vsync](#t5-30); `GX2GetSwapStatus` reports flips pending/executed. shocora holds the [CPU](#t2-1) when more than `MAX_PENDING_FLIPS` are queued. |
| <a id="t5-30"></a>5.30 | Vsync / vertical blank | The moment, 60 times a second, when the screen starts a new picture. | The beat of a metronome. | shocora paces the whole emulation by it. | Same as V-Sync in game settings: it locks the [Swap / flip](#t5-29) to the display's refresh. | 59.94 Hz; signalled to games through `GX2_CB_EVENT_VSYNC` [callbacks](#t4-28) and `GX2WaitForVsync`. shocora raises it at the end of each `run_frame`. |
| <a id="t5-31"></a>5.31 | Swap interval | How many [vsync](#t5-30) beats to wait between flips. 1 → 60 [FPS](#t1-5), 2 → 30 FPS. | Playing on every beat or every second beat. | Breath of the Wild uses 2. | Like `Present(2, 0)` in DirectX: a frame-rate cap at refresh rate ÷ n. | `GX2SetSwapInterval(n)`; a flip may not happen earlier than n [vsyncs](#t5-30) after the previous one. shocora can force a minimum (`min_swap_interval`). |
| <a id="t5-32"></a>5.32 | Timestamp | A number the [GPU](#t2-15) writes when it reaches a point in the order list. | A "you are here" sticker. | Lets the game know how far the [GPU](#t2-15) has got. | Like a GPU fence value: the CPU checks how far the GPU has got without stopping it. | `EVENT_WRITE_EOP` writes a 64-bit counter at end of pipe; `GX2GetRetiredTimeStamp`, `GX2WaitTimeStamp`, `GX2SubmitUserTimeStamp`. shocora's [GPU thread](#t11-8) publishes the retired value atomically. |
| <a id="t5-33"></a>5.33 | `GX2DrawDone` | Waits until the [GPU](#t2-15) has finished everything. | Waiting for the painter to put the brush down. | One of the few places where the [CPU](#t2-1) side has to stop and wait. | Like `glFinish()`: the CPU waits for all GPU work. Here only the calling [thread](#t4-10) waits. | Flushes and waits until the last submitted [timestamp](#t5-32) retires. In shocora the calling [guest](#t1-2) [thread](#t4-10) blocks (`Wait::Gpu`) while other threads keep the [core](#t2-3). |
| <a id="t5-34"></a>5.34 | `GX2Invalidate` | Tells the [GPU](#t2-15) that some memory changed. | "I've changed the recipe, read it again." | Tells shocora which [textures](#t5-14) or buffers to reload. | Manual cache coherency between CPU and GPU (PC drivers do this for you). shocora uses it to know which [textures](#t5-14) and buffers changed. | `GX2Invalidate(mode, ptr, size)` with `GX2_INVALIDATE_MODE_*` ([CPU](#t2-1), attribute buffer, [texture](#t5-14), uniform block, [shader](#t2-17), color/[depth buffer](#t5-18), [stream-out](#t5-13)) → `SURFACE_SYNC`. shocora uses CPU invalidations as write notifications. |
| <a id="t5-35"></a>5.35 | GX2R | A newer helper layer on top of [GX2](#t5-1) for managing buffers. | Pre-printed order forms. | Used by many later games. | A helper layer that tracks buffer usage for the game, a step towards what DirectX 11 does automatically. | `GX2RBuffer`/`GX2RSurface` with `GX2R_RESOURCE_BIND_*` usage flags; `GX2RLockBufferEx`/`GX2RUnlockBufferEx` perform the [cache](#t2-5) maintenance; allocator set by `GX2RSetAllocator`. |
| <a id="t5-36"></a>5.36 | Occlusion query | Asks the [GPU](#t2-15) how many pixels of something were visible. | "Can anyone see this?" | Used to skip hidden objects and for lens flares. | Same as occlusion queries in DirectX/OpenGL. | `ZPASS_DONE` events write begin/end sample counters for each of 8 DBs; `GX2QueryBegin`/`GX2QueryEnd`/`GX2QueryGetOcclusionResult`. |
| <a id="t5-37"></a>5.37 | Pipeline | A ready-to-use combination of [shaders](#t2-17) and drawing settings on a PC graphics card. | A fully set-up painting station. | Building one takes milliseconds, which causes [stutter](#t1-6) the first time an effect appears. shocora keeps them in a [cache](#t2-5). | Same as a Vulkan/DX12 pipeline state object. Because the Wii U has none, the emulator builds one for every new combination of [shaders](#t2-17) and settings it sees. | `wgpu::RenderPipeline` → `VkPipeline`/`ID3D12PipelineState`; keyed by ([vertex shader](#t5-9), [pixel shader](#t5-10), state hash). Unused ones expire after `PIPELINE_EXPIRE_FLIPS`. |
| <a id="t5-38"></a>5.38 | Shader cache / pipeline cache | Translated [shaders](#t2-17) and [pipelines](#t5-37) saved on disk for next time. | Pre-cut ingredients in the freezer. | Removes most first-time [stutter](#t1-6) on the next run. | Same as the shader cache in your GPU driver or Steam's shader pre-caching. | [Cemu](#t11-16) keeps a per-title transferable [cache](#t2-5) of translated [shaders](#t2-17) plus the driver's [pipeline](#t5-37) cache; shocora persists a `wgpu::PipelineCache` (`VkPipelineCache`) per [title](#t8-1). |
| <a id="t5-39"></a>5.39 | wgpu / Vulkan / DirectX 12 | The ways a PC program talks to your graphics card. | The language you use to give orders to your own painter. | shocora uses wgpu, which speaks Vulkan, DirectX 12 or OpenGL underneath. | wgpu is a Rust graphics library that implements WebGPU on top of Vulkan, DirectX 12, Metal and OpenGL, so shocora's renderer is written once. | wgpu = wgpu-core (validation, resource tracking) over wgpu-hal backends; WGSL is compiled by naga to SPIR-V/HLSL/GLSL. Per-call validation is part of the [render thread](#t11-9)'s cost. |

| <a id="t6-5"></a>6.5 | Audio frame | The 3-millisecond chunk the sound engine works in. | One bar of music. | The game must supply new sound every 3 ms or you hear crackles. | The audio buffer size: the engine wakes every 3 ms to mix the next chunk. Late chunks cause crackling. | 3 ms = 96 samples at 32 kHz; `AXRegisterFrameCallback` / `AXRegisterAppFrameCallback` run every frame to update [voices](#t6-2). |
| <a id="t6-6"></a>6.6 | DRC audio | The sound coming out of the [GamePad](#t2-26)'s speaker. | The second set of speakers. | Mixed separately from the [TV](#t2-28) sound. | A second audio output, like headphones and speakers at once. | A separate mix (mono/stereo/surround) encoded and streamed with the [GamePad](#t2-26) video. |

| # | Term | In plain words | Picture it as | Why it matters | For intermediates | For experts |
| ---: | --- | --- | --- | --- | --- | --- |
| <a id="t8-1"></a>8.1 | Title | Any installable piece of software: a game, update, [DLC](#t8-8) or system app. | A book in a library. | What shocora's game list shows. | Like a package on a console store: base games, [updates](#t8-7) and [DLC](#t8-8) are separate titles. | Identified by a 64-bit [title ID](#t8-2); installed under `usr/title/<high>/<low>/` with [`code/`](#t8-3), [`content/`](#t8-4), [`meta/`](#t8-5). |
| <a id="t8-2"></a>8.2 | Title ID | A 16-digit number identifying a [title](#t8-1), e.g. `00050000101C9300`. The same low half in different types links a game to its [Update](#t8-7) and [DLC / AOC](#t8-8). | High 32 bits = type: `00050000` app, `0005000E` update, `0005000C` [AOC](#t8-8), `00050010` system app, `0005001B` system data; low 32 bits identify the product and region. |

| <a id="t8-4"></a>8.4 | `content/` folder | The game's data: models, [textures](#t5-14), sound, maps. | The ingredients. | Appears to the game as `/vol/content`. | Like a game's `data` or `assets` folder. | Arbitrary layout per game (BotW: SARC/BFRES/BNTX archives, Yaz0- or zstd-compressed); mounted read-only. |
| <a id="t8-5"></a>8.5 | `meta/` folder | Name, icon and boot pictures. | The book cover. | Used for the game list. | Like the store page metadata: name, icon, banner. | [`meta.xml`](#t8-6) (names in 12 languages, [title ID](#t8-2), version, product code), `iconTex.tga`, `bootTvTex.tga`, `bootDrcTex.tga`, `bootSound.btsnd`. |
| <a id="t8-6"></a>8.6 | `app.xml` / `cos.xml` / `meta.xml` | Small settings files describing the [title](#t8-1). | The label on the box. | Version, memory settings and name. | Like a manifest file (`AndroidManifest.xml`). | `app.xml`: title_id, title_version, os_version, sdk_version; `cos.xml`: argstr, max_size, max_codesize, default stack size, FS/[IOSU](#t10-1) permissions. |
| <a id="t8-7"></a>8.7 | Update | A newer version of a game, installed separately. | An errata sheet that replaces pages. | shocora layers it over the base game. | Like a game patch that replaces files; the emulator lays it over the base game, like a mod loader. | Contains a full new [`code/`](#t8-3) and only changed [`content/`](#t8-4) files; the system mounts update content over base content, which shocora's overlay `Vfs` reproduces. |
| <a id="t8-8"></a>8.8 | DLC / AOC | Downloadable extra content ("add-on content"). | Bonus chapters. | Reached through [`nn_aoc`](#t9-5). | Same as DLC on PC; the game must open it through [`nn_aoc`](#t9-5). | `AOC_Initialize`, `AOC_ListTitle`, `AOC_OpenTitle` mount `/vol/aoc<titleid>`; access is granted per listed [title](#t8-1). |
| <a id="t8-9"></a>8.9 | Save data | Your progress, stored per user. | A bookmark and notes. | Kept in a normal folder; written when the game says "save now". | Same as save files in your Documents folder; written through [`nn_save`](#t9-2). | `/vol/save/<persistentId>/` (user 0x80000001…) and `/vol/save/common/`; `SAVEInit`, `SAVEOpenFile`, `SAVECommit`; quota from [`cos.xml`](#t8-6). |
| <a id="t8-10"></a>8.10 | File system (FS / FSA) | The system service that opens and reads files. | The library's front desk. | Every file the game loads passes through it. | Like the file APIs of an OS (`CreateFile`, `fopen`), but every request is a message to the security processor ([IPC](#t10-2)). | `FSClient` + `FSCmdBlock`, sync or async with [callbacks](#t4-28)/[message queues](#t4-23); requests go to [`/dev/fsa`](#t10-3) over [IPC](#t10-2). | <a id="t8-11"></a>8.11 | WUD / WUX | A copy of a game disc, raw (WUD) or compressed (WUX). | A photocopy of the whole disc. | One way to give shocora a game. | Like an ISO image of a disc. | WUD: 25 GiB raw dump with encrypted partitions (disc key needed); WUX: WUD with duplicate and zero sectors removed and an index table. |
| <a id="t8-12"></a>8.12 | WUA | [Cemu](#t11-16)'s single-file archive holding a game with its update and [DLC](#t8-8). | A box set. | Another way. | Like a zip of an installed game, read without extracting. | Built on ZArchive: zstd-compressed blocks with a random-access file tree; holds several [titles](#t8-1) (base, update, [DLC](#t8-8)) decrypted. |
| <a id="t8-13"></a>8.13 | NUS format | Encrypted files as downloaded from Nintendo's servers. | A sealed envelope. | Needs decrypting first. | The raw download format, still encrypted ([SEEPROM / OTP](#t2-25)). | `title.tmd` (content list and hashes), `title.tik` (encrypted [title](#t8-1) key), `*.app` (AES-128-CBC), `*.h3` hash trees for hashed contents. |
| <a id="t8-14"></a>8.14 | `mlc01` | The folder that imitates the console's flash storage. | The console's hard drive as a folder. | Shared with [Cemu](#t11-16), so the same games and saves work. | The folder that plays the role of the [NAND / MLC](#t2-23). | Layout `usr/title/…`, `usr/save/<high>/<low>/user/<persistentId>`, `sys/…`; shocora reads [Cemu](#t11-16)'s directory as-is. |

## 10. The security side

| # | Term | In plain words | Picture it as | Why it matters | For intermediates | For experts |
| ---: | --- | --- | --- | --- | --- | --- |
| <a id="t10-1"></a>10.1 | IOSU | The small [operating system](#t4-1) on the security processor that handles storage, USB and network. | The building's back office. | Games send it requests; shocora answers them directly. | Think of it as a second OS on its own chip ([Starbuck](#t2-22)) that owns storage and network; games reach it only through [IPC](#t10-2). | ARM microkernel with isolated processes and resource managers; handles crypto, [title](#t8-1) management (MCP), FS, network, USB. |
| <a id="t10-2"></a>10.2 | IPC | Messages passed between the main [CPU](#t2-1) and the security processor. | Notes slipped under a door. | How file and account requests travel on a real console. | Like calling a local server: `open`, `read`, `ioctl` messages, answered asynchronously. | `IOS_Open/Close/Read/Write/Seek/Ioctl/Ioctlv` (+ `Async` variants with [callbacks](#t4-28)) through IPC buffers in shared memory; results come back via the IPC [interrupt](#t4-27). |
| <a id="t10-3"></a>10.3 | Device (`/dev/fsa` …) | A named service inside [IOSU](#t10-1). | A department in the back office. | Each is a small module in shocora. | Like `/dev/` files on Linux: each name is a service you send requests to. | Examples: `/dev/fsa`, `/dev/mcp`, `/dev/acp_main`, `/dev/socket`, `/dev/crypto`, `/dev/usb_hid`; shocora's `Iosu` routes by path. |
| <a id="t10-4"></a>10.4 | Syscall | A request from a program to the [core](#t2-3) of the [OS](#t4-1). | Ringing the manager's bell. | Games don't use them directly; shocora stops if one appears. | The same as a system call on Linux or Windows. Games don't make them directly; the [`coreinit`](#t4-9) library does. | `sc` with the syscall number in r0; used inside coreinit for kernel services. [HLE](#t4-3) replaces the callers, so a raw `sc` in game code is a bug or anti-emulation. |

## 11. How shocora runs the game (emulator techniques)

| # | Term | In plain words | Picture it as | Why it matters | For intermediates | For experts |
| ---: | --- | --- | --- | --- | --- | --- |
| <a id="t11-1"></a>11.1 | Interpreter | Reads each game instruction and does what it says, one at a time. | Translating a speech live, sentence by sentence. | Exact but slow. Used for code that hasn't been translated yet, and for debugging. | Like a scripting-language interpreter (CPython) running a loop of decode → execute for every [instruction](#t2-6). | `interpreter::step` decodes and executes one instruction; it is the reference semantics, and the [JIT](#t11-2) falls back to it per instruction (`interpret_one`). |
| <a id="t11-2"></a>11.2 | JIT (just-in-time compiler) / recompiler | Translates whole pieces of game code into your PC's own instructions the first time they run, then reuses the translation. | Translating a book chapter once, then just reading the translation. | Most of the game's code runs this way. Much faster than the [interpreter](#t11-1). | Like the JIT in Java or JavaScript engines, but the input is machine code ([PowerPC](#t2-7)) instead of bytecode. New code runs on the [Interpreter](#t11-1) until its translation is ready, which avoids stalls but causes brief slowdowns ([Stutter](#t1-6)). | Two tiers: quick translation ([Cranelift](#t11-3) `opt_level=none`, straight-line block ≤ 64 instructions) queued to worker [threads](#t4-10), then hot blocks re-translated as optimized regions. Blocks chain through a page table with tail calls. |
| <a id="t11-3"></a>11.3 | Cranelift | The code-generator [library](#t4-5) shocora's [JIT](#t11-2) uses to produce PC instructions. | The translator's dictionary and grammar book. | Decides how fast the translated code is. | A compiler back end like LLVM, but designed to compile quickly, which suits a [JIT (just-in-time compiler) / recompiler](#t11-2). | SSA-based code generator from the Bytecode Alliance (Wasmtime); compiles much faster than LLVM with fewer optimizations; shocora uses its `tail` calling convention. |
| <a id="t11-4"></a>11.4 | Block / region | A short run of game instructions translated together (block), or a larger area including loops (region). | A sentence, or a whole paragraph. | [Hot code](#t11-5) is retranslated as regions to run faster. | The units the [JIT (just-in-time compiler) / recompiler](#t11-2) translates. A region covers a whole loop, so it runs without jumping back to the emulator. | Region: up to 256 instructions within ±16 KiB following branches, with extra entries at call return [addresses](#t3-1) so returns land inside the same code. |
| <a id="t11-5"></a>11.5 | Hot code | Code that runs very often. | The phrases you use every day. | Worth translating carefully. Code that ran once at start-up isn't. | Like profile-guided optimization at run time: only code that runs often gets the slower, better translation. | Each quick block increments a counter in memory; a block is queued for optimization at `HOT_RUNS` (1,000). The hot scan walks candidates in batches of 16,384. |
| <a id="t11-6"></a>11.6 | Code cache | Memory holding all translated code. | The shelf of finished translations. | It can grow to hundreds of megabytes. shocora packs it tightly and lets go of rarely used translations when it gets too big. | Like a browser's JIT memory: it grows with the amount of code that ran. shocora caps the cheap translations and frees them between frames ([Working set / memory usage](#t11-15)). | [Cranelift](#t11-3) `JITModule`s backed by `CodeMemory` (64 MiB chunks, executable after each batch). Quick translations sit in their own module and are released at a frame boundary past 256 MiB. Measured in BotW: ~240 MB quick + ~530 MB optimized. |
| <a id="t11-7"></a>11.7 | Multi-core mode | Each of the Wii U's three [cores](#t2-3) runs on its own PC [thread](#t4-10) at the same time. | Three cooks working at once instead of taking turns. | Up to three times faster on the [CPU](#t2-1) side, as in [Cemu](#t11-16). | Three host threads for three guest [cores](#t2-3), sharing guest memory. The OS part is shared too, so it is protected by a [Lock (in the emulator)](#t11-10). | Per frame, [cores](#t2-3) 0 and 2 run on scoped [threads](#t4-10) and core 1 on the caller; [HLE](#t4-3) calls and scheduling take one machine lock; the [JIT](#t11-2) page table is read without locking. |
| <a id="t11-8"></a>11.8 | GPU thread | A PC [thread](#t4-10) that only processes the game's drawing orders. | A separate assistant who sorts the order forms. | The [CPU](#t2-1) side doesn't wait for drawing. | Like a render thread in a game engine: the game thread queues work, the GPU thread processes it in parallel. | Executes [PM4](#t5-3) and produces `RenderCommand`s; the [CPU](#t2-1) blocks only on [`GX2DrawDone`](#t5-33), [timestamps](#t5-32), or being `MAX_FRAMES_AHEAD` (2) frames ahead. |
| <a id="t11-9"></a>11.9 | Render thread | A PC [thread](#t4-10) that talks to your graphics card. | The person who actually hands orders to your painter. | Keeps the graphics driver's slow work away from the game logic. | The thread that calls wgpu ([wgpu / Vulkan / DirectX 12](#t5-39)); keeping driver calls here stops them from slowing down the emulation threads. | Owns the [wgpu](#t5-39) device; consumes command batches through a bounded channel (3); records [texture](#t5-14) uploads into the encoder via a 32 MiB staging ring and coalesces arena writes. |
| <a id="t11-10"></a>11.10 | Lock (in the emulator) | A rule that only one PC [thread](#t4-10) changes shared [emulator](#t1-1) data at a time. | The talking stick in a meeting. | Waiting for it wastes time. Making common operations not need it ("[fast calls](#t11-11)") was a big speed-up. | A plain mutex in the emulator's own code (not the guest's [Mutex (OSMutex, OSFastMutex)](#t4-17)). The fewer guest calls need it, the less the cores wait for each other ([Fast call](#t11-11)). | A `std::sync::Mutex` around `CafeOs`, `Gpu` and `Iosu`; profiling reports wait time per [core](#t2-3) (`lock` in `SHOCORA_PROFILE`). |
| <a id="t11-11"></a>11.11 | Fast call | A system function simple enough to run without the shared lock (memory copy, time, [thread](#t4-10) data). | Grabbing a pen from your own desk instead of asking the office. | Keeps the three [cores](#t2-3) from waiting for each other. | An [HLE (high-level emulation)](#t4-3) function that only touches the calling core's own data, so it skips the [Lock (in the emulator)](#t11-10). | `wiiu_cafe_os::fast`: memcpy/memset, [cache](#t2-5) ops, [core](#t2-3) id, time, thread-specific slots, `__tls_get_addr` after first use; writes are forwarded to the [GPU](#t2-15)'s write tracker. Each must equal its locked version (tested). |
| <a id="t11-12"></a>11.12 | Graphics pack | [Cemu](#t11-16)'s add-ons that change resolution, frame rate or [shaders](#t2-17). | Mod kits. | shocora offers similar options in its settings. | Cemu's mods: shader replacements, [Resolution factor](#t11-13) changes and FPS patches. | `rules.txt` plus [shader](#t2-17) replacements keyed by shader hash, resolution rules matching [texture](#t5-14) sizes, and assembly patches for game code. |
| <a id="t11-13"></a>11.13 | Resolution factor | Drawing the game's pictures N times larger than the console did. | Printing a photo at a bigger size. | Sharper picture; costs graphics-card time and memory. | Like internal resolution scaling in game settings, applied to a game that doesn't have that option. | Scales targets that match the [TV](#t2-28) picture (shadow maps keep their size), up to 10,240 pixels wide; steps down on out-of-memory. |
| <a id="t11-14"></a>11.14 | Save state | A snapshot of the whole emulated console at one moment. | Pausing a film and saving the exact frame. | Different from the game's own save files. | Like a VM snapshot: the whole machine's memory and [registers](#t2-9) at one instant. | postcard-serialized [CPU](#t2-1)/[OS](#t4-1)/[GPU](#t2-15) state plus lz4-compressed [guest](#t1-2) memory and [host](#t1-3) [surfaces](#t5-16); versioned, so a different build rejects it. |
| <a id="t11-15"></a>11.15 | Working set / memory usage | How much of your PC's RAM the [emulator](#t1-1) is using right now. | How much of the table your project covers. | Lower is better: it leaves room for other programs. | The "Memory" column in Task Manager. For shocora the main parts are guest memory ([MEM2](#t2-21)), translated code ([Code cache](#t11-6)) and the renderer's caches. | Resident pages (Task Manager "Memory"); differs from commit charge. In BotW: [guest](#t1-2) memory ~1.1 GB, [JIT](#t11-2) code ~0.8 GB, [heap](#t3-6) and driver memory for the rest. |
| <a id="t11-16"></a>11.16 | Cemu | The most mature Wii U [emulator](#t1-1), written in C++. | An experienced colleague. | shocora often copies Cemu's proven approaches. | The reference implementation many emulator ideas are checked against; its source code is public. | Open source (MPL-2.0) since 2022; custom PPC→x86-64 [recompiler](#t11-2) via its own IR, [Vulkan](#t5-39)/OpenGL [Latte](#t2-16) renderer with async [shader](#t2-17) compilation, [HLE](#t4-3) coreinit with fiber-based [threads](#t4-10). |
