# Wii U Terms, Explained for Beginners

This page is for anyone who wants to understand how a Wii U emulator works, even if you have never looked inside a game console before. Each term gets one row in a table:

- **In plain words**: what the thing is.
- **Picture it as**: an everyday comparison to help you imagine it.
- **Why it matters**: what it does on a real Wii U, and what shocora (this emulator) does about it.
- **For experts**: registers, API names, data layouts and implementation details, for when you read the code.

Rows are numbered by chapter (2.5 is the fifth term of chapter 2), so you can point to a term.

You don't need to read it in order. Start with "The big picture", then look up words as you meet them.

---

## 1. The big picture: what an emulator does

A game console is a small computer with its own processor, graphics chip, memory and operating system. A game is a program written only for that machine. Your PC can't run it directly: it speaks a different "language" (instruction set), has a different graphics chip, and doesn't have the Wii U's operating system.

An **emulator** is a program that pretends to be the console. Imagine a translator, a stage crew and a fake post office all working together so that an actor (the game) believes it is performing on its usual stage:

1. **The CPU part** reads the game's instructions and does the same work on your PC's processor (the translator).
2. **The graphics part** reads the drawing orders the game sends to the Wii U's graphics chip and redraws the picture with your PC's graphics card (the stage crew).
3. **The operating-system part** answers the game's requests ("open this file", "start a thread", "play this sound") the way the Wii U's system software would (the post office).

When all three keep up with the game, it runs at full speed. When one falls behind, the game stutters or slows down.

## 2. Hardware: the parts inside the console

The Wii U has three main chips: a **CPU** (the thinker), a **GPU** (the painter) and a small **security processor** (the gatekeeper). Around them are memory, flash storage, and the controllers.

## 3. Memory and addresses

Memory is a very long row of numbered boxes, each holding one byte. A box's number is its **address**. Programs find their data by address.

|    # | Term              | In plain words                                                                         | Picture it as                                                                        | Why it matters                                                                                                                  | For experts                                                                                                                                                                                 |
| ---: | ----------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
|  3.1 | Address           | The number of a memory location.                                                       | A house number on a very long street.                                                | Every pointer in the game is an address.                                                                                        | 32-bit effective addresses; Cafe OS uses fixed BAT/page-table mappings per process, so games never change translation.                                                                      |
|  3.2 | Address space     | All addresses a program can use. The Wii U CPU uses 32-bit addresses, so 4 GB of them. | The whole street, even where no houses are built yet.                                | shocora reserves one 4 GB block on your PC, so "guest address X" is simply "start of block + X". That makes memory access fast. | `AddressSpace` reserves 4 GiB (`VirtualAlloc(MEM_RESERVE)` / `mmap(PROT_NONE)`) and commits regions on mapping; the JIT accesses `base + ea` without bounds checks.                         |
|  3.3 | Effective address | An address as the game's code sees it.                                                 | The street address on an envelope.                                                   | What the CPU uses.                                                                                                              | What every load/store, branch target and pointer in guest data uses.                                                                                                                        |
|  3.4 | Physical address  | An address as the hardware (GPU, disk transfers) sees it.                              | The GPS coordinates of the same house.                                               | The GPU's orders contain physical addresses; shocora converts them back.                                                        | PM4 packets and GX2 registers carry physical addresses; `wiiu_mem_addr::effective_to_physical`/inverse map MEM1, MEM2 and the foreground area.                                              |
|  3.5 | Code area         | Where the game's program is loaded (starting at `0x02000000`).                         | The shelf where the recipe book sits.                                                | If a game rewrites its own code, shocora must throw away translations of that code.                                             | RPX `.text` loads at `0x02000000`, data at `0x10000000`; `ICInvalidateRange` or writes there invalidate JIT entries in the overlapping range.                                               |
|  3.6 | Heap              | A pool of memory the game hands out piece by piece as it needs it.                     | A shared pantry where you take containers as needed.                                 | The Wii U system offers several kinds (expanding, frame, unit heaps); shocora implements them.                                  | `MEMExpHeap` (free list, best/first fit, both ends), `MEMFrmHeap` (push/pop states), `MEMUnitHeap` (fixed blocks); default heap via `MEMGetBaseHeapHandle` and `MEMAllocFromDefaultHeapEx`. |
|  3.7 | Foreground bucket | Memory reserved for the app on screen, taken back when it goes to the background.      | A table at a restaurant you keep only while you're seated.                           | Some games use it for screenshots and temporary data.                                                                           | `OSGetForegroundBucket` / `OSGetForegroundBucketFreeArea`; ProcUI asks the app to save it before releasing the foreground.                                                                  |
|  3.8 | Cache line        | The 32-byte chunk the CPU cache works in.                                              | The size of one scoop.                                                               | The game's "flush this range" requests come in cache lines, and they tell shocora which memory the GPU should re-read.          | 32 bytes; `dcbz` zeroes one, `DCFlushRange` rounds to them. shocora's `WriteTracker` stamps 4 KiB pages so the GPU re-hashes only what changed.                                             |
|  3.9 | Aperture          | A window that shows a GPU image in simple row-by-row order.                            | A window that rearranges a jigsaw puzzle into a flat picture as you look through it. | A few games read rendered pictures through it.                                                                                  | `GX2AllocateTilingApertureEx` programs a hardware window that detiles on access; shocora must serve linear views of tiled surfaces.                                                         |

## 4. The operating system (Cafe OS)

A game doesn't talk to the hardware directly for most things. It calls ready-made functions in the console's **operating system** (Cafe OS): "start a thread", "allocate memory", "open a file". shocora rewrites those functions itself instead of running Nintendo's code.

| ---: | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
|  4.1 | Operating system (OS)                             | The base software that manages the hardware and offers services to programs.                                             | The building management: electricity, water, mail, keys.                                                | Games depend on it for nearly everything.                                                                                                 | Cafe OS: a PowerPC kernel plus RPL libraries in user space; multi-process (game, HOME Menu, overlays) with per-process address spaces.                                                                                                       |

| 4.27 | Interrupt                                         | A hardware signal that makes the CPU stop and handle something urgent.                                                   | A phone ringing while you cook.                                                                         | The screen refresh and "GPU finished" events arrive this way.                                                                             | Sources: decrementer, IPC, GPU (EOP, vsync, flip), DMA; delivered via the PI interrupt controller to kernel handlers.                                                                                                                        |
| 4.28 | Callback                                          | A function the game gives the system, to be called later when something happens.                                         | Leaving your number: "call me when it's ready".                                                         | shocora calls them at the right moments, for example when a frame is shown.                                                               | shocora runs guest callbacks (`GuestCall`) on a borrowed core with a return trampoline, after saving and before restoring the interrupted context.                                                                                           |
| 4.29 | `proc_ui`                                         | The library that tells a game whether it is on screen, in the background or closing.                                     | The stage manager saying "you're on" or "take a break".                                                 | shocora always says "you're on screen".                                                                                                   | `ProcUIProcessMessages` returns `PROCUI_STATUS_IN_FOREGROUND` / `_RELEASE_FOREGROUND` / `_EXITING`; release callbacks must free GPU and foreground memory.                                                                                   |
| 4.30 | HOME Menu                                         | The overlay that pauses the game when you press HOME.                                                                    | An intermission.                                                                                        | Not imitated.                                                                                                                             | A separate process that takes the foreground; the game releases GX2 resources, then reacquires them on return.                                                                                                                               |
| 4.31 | `OSDynLoad`                                       | Loading a library while the game is running.                                                                             | Fetching an extra manual from the shelf mid-task.                                                       | shocora answers with its own functions.                                                                                                   | `OSDynLoad_Acquire`, `OSDynLoad_FindExport`, `OSDynLoad_Release`; also used by the system to resolve `*.rpl` imports.                                                                                                                        |
| 4.32 | `__ghsLock`                                       | The lock protecting the C standard library inside the game (memory allocation, text output).                             | The key to the shared supply cupboard.                                                                  | Another very frequently used lock.                                                                                                        | Green Hills MULTI runtime hooks (`__ghsLock`/`__ghsUnlock`) protecting malloc and stdio; recursive per thread.                                                                                                                               |

## 5. Graphics (GX2 and Latte)

To draw a frame, a game doesn't paint pixels itself. It sends a long list of orders to the GPU: "use this texture", "use this shader", "draw these triangles". GX2 is the Wii U library for writing those orders.

## 11. How shocora runs the game (emulator techniques)

|     # | Term                                     | In plain words                                                                                                             | Picture it as                                                       | Why it matters                                                                                                               | For experts                                                                                                                                                                                                                                    |
| ----: | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
|  11.1 | Interpreter                              | Reads each game instruction and does what it says, one at a time.                                                          | Translating a speech live, sentence by sentence.                    | Exact but slow. Used for code that hasn't been translated yet, and for debugging.                                            | `interpreter::step` decodes and executes one instruction; it is the reference semantics, and the JIT falls back to it per instruction (`interpret_one`).                                                                                       |
|  11.2 | JIT (just-in-time compiler) / recompiler | Translates whole pieces of game code into your PC's own instructions the first time they run, then reuses the translation. | Translating a book chapter once, then just reading the translation. | Most of the game's code runs this way. Much faster than the interpreter.                                                     | Two tiers: quick translation (Cranelift `opt_level=none`, straight-line block ≤ 64 instructions) queued to worker threads, then hot blocks re-translated as optimized regions. Blocks chain through a page table with tail calls.              |
|  11.3 | Cranelift                                | The code-generator library shocora's JIT uses to produce PC instructions.                                                  | The translator's dictionary and grammar book.                       | Decides how fast the translated code is.                                                                                     | SSA-based code generator from the Bytecode Alliance (Wasmtime); compiles much faster than LLVM with fewer optimizations; shocora uses its `tail` calling convention.                                                                           |
|  11.4 | Block / region                           | A short run of game instructions translated together (block), or a larger area including loops (region).                   | A sentence, or a whole paragraph.                                   | Hot code is retranslated as regions to run faster.                                                                           | Region: up to 256 instructions within ±16 KiB following branches, with extra entries at call return addresses so returns land inside the same code.                                                                                            |
|  11.5 | Hot code                                 | Code that runs very often.                                                                                                 | The phrases you use every day.                                      | Worth translating carefully. Code that ran once at start-up isn't.                                                           | Each quick block increments a counter in memory; a block is queued for optimization at `HOT_RUNS` (1,000). The hot scan walks candidates in batches of 16,384.                                                                                 |
|  11.6 | Code cache                               | Memory holding all translated code.                                                                                        | The shelf of finished translations.                                 | It can grow to hundreds of megabytes. shocora packs it tightly and lets go of rarely used translations when it gets too big. | Cranelift `JITModule`s backed by `CodeMemory` (64 MiB chunks, executable after each batch). Quick translations sit in their own module and are released at a frame boundary past 256 MiB. Measured in BotW: ~240 MB quick + ~530 MB optimized. |
|  11.7 | Multi-core mode                          | Each of the Wii U's three cores runs on its own PC thread at the same time.                                                | Three cooks working at once instead of taking turns.                | Up to three times faster on the CPU side, as in Cemu.                                                                        | Per frame, cores 0 and 2 run on scoped threads and core 1 on the caller; HLE calls and scheduling take one machine lock; the JIT page table is read without locking.                                                                           |
|  11.8 | GPU thread                               | A PC thread that only processes the game's drawing orders.                                                                 | A separate assistant who sorts the order forms.                     | The CPU side doesn't wait for drawing.                                                                                       | Executes PM4 and produces `RenderCommand`s; the CPU blocks only on `GX2DrawDone`, timestamps, or being `MAX_FRAMES_AHEAD` (2) frames ahead.                                                                                                    |
|  11.9 | Render thread                            | A PC thread that talks to your graphics card.                                                                              | The person who actually hands orders to your painter.               | Keeps the graphics driver's slow work away from the game logic.                                                              | Owns the wgpu device; consumes command batches through a bounded channel (3); records texture uploads into the encoder via a 32 MiB staging ring and coalesces arena writes.                                                                   |
| 11.10 | Lock (in the emulator)                   | A rule that only one PC thread changes shared emulator data at a time.                                                     | The talking stick in a meeting.                                     | Waiting for it wastes time. Making common operations not need it ("fast calls") was a big speed-up.                          | A `std::sync::Mutex` around `CafeOs`, `Gpu` and `Iosu`; profiling reports wait time per core (`lock` in `SHOCORA_PROFILE`).                                                                                                                    |
| 11.11 | Fast call                                | A system function simple enough to run without the shared lock (memory copy, time, thread data).                           | Grabbing a pen from your own desk instead of asking the office.     | Keeps the three cores from waiting for each other.                                                                           | `wiiu_cafe_os::fast`: memcpy/memset, cache ops, core id, time, thread-specific slots, `__tls_get_addr` after first use; writes are forwarded to the GPU's write tracker. Each must equal its locked version (tested).                          |
| 11.12 | Graphics pack                            | Cemu's add-ons that change resolution, frame rate or shaders.                                                              | Mod kits.                                                           | shocora offers similar options in its settings.                                                                              | `rules.txt` plus shader replacements keyed by shader hash, resolution rules matching texture sizes, and assembly patches for game code.                                                                                                        |
| 11.13 | Resolution factor                        | Drawing the game's pictures N times larger than the console did.                                                           | Printing a photo at a bigger size.                                  | Sharper picture; costs graphics-card time and memory.                                                                        | Scales targets that match the TV picture (shadow maps keep their size), up to 10,240 pixels wide; steps down on out-of-memory.                                                                                                                 |
| 11.14 | Save state                               | A snapshot of the whole emulated console at one moment.                                                                    | Pausing a film and saving the exact frame.                          | Different from the game's own save files.                                                                                    | postcard-serialized CPU/OS/GPU state plus lz4-compressed guest memory and host surfaces; versioned, so a different build rejects it.                                                                                                           |
| 11.15 | Working set / memory usage               | How much of your PC's RAM the emulator is using right now.                                                                 | How much of the table your project covers.                          | Lower is better: it leaves room for other programs.                                                                          | Resident pages (Task Manager "Memory"); differs from commit charge. In BotW: guest memory ~1.1 GB, JIT code ~0.8 GB, heap and driver memory for the rest.                                                                                      |
| 11.16 | Cemu                                     | The most mature Wii U emulator, written in C++.                                                                            | An experienced colleague.                                           | shocora often copies Cemu's proven approaches.                                                                               | Open source (MPL-2.0) since 2022; custom PPC→x86-64 recompiler via its own IR, Vulkan/OpenGL Latte renderer with async shader compilation, HLE coreinit with fiber-based threads.                                                              |
