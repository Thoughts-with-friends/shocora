# はじめての Wii U 用語解説

このページは、ゲーム機の中身を見たことがない人でも Wii U エミュレータの仕組みがわかるように書いた用語集です。1 行に 1 つの用語を、次の観点で説明しています。

- **ひとことで**：それが何か。
- **たとえるなら**：イメージしやすい身近なたとえ。
- **なぜ大事か**：本物の Wii U での役割と、shocora（このエミュレータ）がそれをどう扱うか。
- **中級者向けの詳細**：PC でゲームをよく遊び、プログラムも書くけれど、ゲーム機やエミュレータの知識はない人向け。Windows、DirectX、`std::thread` など、すでに知っているものと比べ、他の用語とのつながりも示す。
- **専門家向けの詳細**：レジスタ、API 名、データ構造、実装の細部。コードを読むときの手がかり。

1 行を左から右へ読むと、列ごとに一段ずつ詳しくなります。

各行には章ごとの番号（2.5 なら第 2 章の 5 番目）が付いているので、用語を番号で指し示せます。[レジスタ](#t2-9) のようなリンクをクリックすると、その用語の行へ移動します。

最初から順に読む必要はありません。まず「全体像」を読み、あとは出てきた言葉を調べる辞書として使ってください。

## 1. 全体像：エミュレータは何をしているのか

ゲーム機は、専用の CPU・グラフィックチップ・メモリ・OS を持つ小さなコンピュータです。ゲームはその機械のためだけに書かれたプログラムなので、PC ではそのままでは動きません。PC は「話す言葉」（命令セット）が違い、グラフィックチップも違い、Wii U の OS も入っていないからです。

**エミュレータ**は、ゲーム機のふりをするプログラムです。役者（ゲーム）がいつもの舞台で演じていると思い込めるように、通訳・舞台スタッフ・代わりの郵便局がチームで働いている、と想像してください。

1. **CPU 担当**：ゲームの命令を読み、同じ仕事を PC の CPU で行う（通訳）。
2. **グラフィック担当**：ゲームが Wii U のグラフィックチップに送る「描画の指示」を読み、PC のグラフィックカードで描き直す（舞台スタッフ）。
3. **OS 担当**：「このファイルを開いて」「スレッドを始めて」「この音を鳴らして」といったゲームからの頼みごとに、Wii U の OS と同じように答える（郵便局）。

3 つ全部がゲームのペースについていければ、ゲームは本来の速さで動きます。どれか 1 つでも遅れると、カクついたり遅くなったりします。

## 2. ハードウェア：ゲーム機の中の部品

Wii U の中心には 3 つのチップがあります。**CPU**（考える係）、**GPU**（絵を描く係）、そして小さな**セキュリティ用プロセッサ**（門番）です。その周りにメモリ、フラッシュストレージ、コントローラーがあります。

| ---: | --- | --- | --- | --- | --- | --- |
| <a id="t2-1"></a>2.1 | CPU | プログラムの命令を 1 つずつ実行するチップ。 | レシピを一行ずつ実行する頭脳。 | 敵の動き、物理、メニューなど、ゲームが「判断」することはすべてここで起きる。 | 原理は PC の CPU と同じだが、ずっと古くて単純。SSE / AVX のような SIMD はなく、[キャッシュ](#t2-5) も小さく、[コア](#t2-3) は 3 つ。 | PowerPC 750 派生のスーパースカラ。コアごとに L1 命令 / データ各 32 KiB、ラインは 32 バイト。AltiVec はない。 |
| <a id="t2-2"></a>2.2 | Espresso | Wii U の CPU の名前（IBM 製）。約 1.24 GHz のコアが 3 つある。 | 1 つの台所を 3 人の料理人で使う状態。 | shocora は 3 人を同時に、十分な速さでまねる必要がある。ブレワイを快適に動かす上で一番難しいところ。 | ゲームキューブと Wii の CPU の子孫。1 コアの性能は今の PC のコアよりはるかに低いが、エミュレートするとゲストの 1 命令にホストの命令がいくつも必要になる（[インタプリタ](#t11-1)、[JIT（ジャストインタイムコンパイラ）/ リコンパイラ](#t11-2)）。 | 750CL 派生コア 3 基、1.243125 GHz、バス 248.625 MHz。L2 はコア 0 / 1 / 2 で 512 KiB / 2 MiB / 512 KiB。 |
| <a id="t2-3"></a>2.3 | コア | CPU の中で独立して働く作業員。Wii U はコア 0・1・2 の 3 つ。 | 3 人の料理人のうちの 1 人。 | ゲームは仕事を各コアに分ける。コア 1 が「メイン」で、ゲームの起動や描画の指示出しを担当することが多い。 | PC の CPU のコアと同じだが、どのスレッドをどこで動かすかはゲームが決める（[アフィニティ](#t4-13)）。コア 1 は [キャッシュ](#t2-5) が一番大きく、メインのゲームループを動かす。 | コア番号は SPR UPIR（1007）で読める。`OSGetCoreId` が返す値。shocora のメインコア（`CALLBACK_CORE`）はコア 1。 |

| <a id="t2-13"></a>2.13 | タイムベース | 電源を入れてから 1 秒に約 6,200 万回ずつ増えていくカウンタ。 | 台所の時計。 | ゲームは時間を測るためにこれを読む。shocora は PC の時計から計算し、正しい速さで時間を進める。 | `QueryPerformanceCounter` や `clock_gettime` のようなもの。一定速度で増える単調なカウンタで、タイムアウト、スリープ、フレームのタイミングはすべてこれが基準。 | `mftb`（TBL / TBU）で読む。shocora は `Instant` をゲーム速度に合わせて換算して tick を出すので、一時停止や 2 倍速でも時間の整合が保たれる。 |

## 3. メモリとアドレス

メモリは、1 バイトずつ入る箱がとても長く並んだものです。箱の番号を**アドレス**と呼び、プログラムはアドレスでデータを探します。

| # | 用語 | ひとことで | たとえるなら | なぜ大事か | 中級者向けの詳細 | 専門家向けの詳細 |
| ---: | --- | --- | --- | --- | --- | --- |
| <a id="t3-1"></a>3.1 | アドレス | メモリの場所を表す番号。 | とても長い通りの番地。 | ゲームの中の「ポインタ」はすべてアドレス。 | C のポインタの値と同じ。ゲストのポインタは 32 ビットなので、すべてが 4 GB に収まる。 | 実効アドレスは 32 ビット。Cafe OS はプロセスごとに固定の BAT / ページテーブル対応を使うので、ゲームが変換を変えることはない。 |
| <a id="t3-2"></a>3.2 | アドレス空間 | プログラムが使えるアドレスの全範囲。Wii U の CPU は 32 ビットなので 4 GB 分。 | まだ家が建っていない区画も含めた、通り全体。 | shocora は PC 上に 4 GB のひとかたまりを予約するので、「ゲストのアドレス X」は「かたまりの先頭 + X」で済み、メモリアクセスが速くなる。 | プロセスの仮想メモリと同じ考え方。shocora は 4 GB の仮想領域を 1 つ予約するので、ゲストのアドレス X はホストでは単に `base + X` になり、[JIT（ジャストインタイムコンパイラ）/ リコンパイラ](#t11-2) は 1 命令でゲストメモリに触れる。 | `AddressSpace` が 4 GiB を予約し（`VirtualAlloc(MEM_RESERVE)` / `mmap(PROT_NONE)`）、領域を割り当てたときにコミットする。JIT は境界チェックなしで `base + ea` にアクセスする。 |
| <a id="t3-3"></a>3.3 | 実効アドレス | ゲームのコードから見たアドレス。 | 封筒に書く住所。 | CPU が使うのはこちら。 | ゲームのコードが使うアドレス（[アドレス](#t3-1)）。Wii U では [物理アドレス](#t3-4) と固定のオフセットしか違わない。 | ゲストのロード / ストア、分岐先、データ中のポインタはすべてこれを使う。 |
| <a id="t3-4"></a>3.4 | 物理アドレス | ハードウェア（GPU やデータ転送）から見たアドレス。 | 同じ家の GPS 座標。 | GPU への指示には物理アドレスが入っているので、shocora が変換し直す。 | GPU や DMA は CPU のアドレス変換を通らないので、[コマンドバッファ](#t5-2) には物理アドレスが入っている。エミュレータはそれを [実効アドレス](#t3-3) に戻す。 | PM4 パケットと GX2 レジスタは物理アドレスを持つ。`wiiu_mem_addr::effective_to_physical` とその逆変換が MEM1、MEM2、フォアグラウンド領域を対応づける。 |
| <a id="t3-5"></a>3.5 | コード領域 | ゲームのプログラムが読み込まれる場所（`0x02000000` から）。 | レシピ本が置いてある棚。 | ゲームが自分のコードを書き換えたら、shocora はそのコードの翻訳を捨てる必要がある。 | [RPX](#t4-6) が読み込まれる場所。ゲームがそこに書き込んだら（まれ）、その範囲の翻訳済みコードを捨てる必要がある（[コードキャッシュ](#t11-6)）。 | RPX の `.text` は `0x02000000`、データは `0x10000000` に読み込まれる。`ICInvalidateRange` やそこへの書き込みで、重なる範囲の JIT エントリが無効化される。 |
| <a id="t3-6"></a>3.6 | ヒープ | ゲームが必要に応じて少しずつ切り出して使うメモリのたまり場。 | 必要なときに容器を取っていく共用の食料庫。 | Wii U の OS には何種類か（拡張ヒープ、フレームヒープ、ユニットヒープ）あり、shocora が実装している。 | `malloc` のようなものだが、ゲームが何種類かの確保方式から選ぶ。管理するのはホストではなくゲストの [MEM2](#t2-21) の中のメモリ。 | `MEMExpHeap`（空きリスト、ベストフィット / ファーストフィット、両端から確保）、`MEMFrmHeap`（状態の push / pop）、`MEMUnitHeap`（固定サイズブロック）。デフォルトヒープは `MEMGetBaseHeapHandle` と `MEMAllocFromDefaultHeapEx` で使う。 |
| <a id="t3-7"></a>3.7 | フォアグラウンドバケット | 画面に出ているアプリ用に取っておかれ、裏に回ると返却されるメモリ。 | 座っている間だけ使えるレストランの席。 | スクリーンショットや一時データに使うゲームがある。 | 画面に出ているアプリのものになるメモリ。裏に回るときは返さなければならない（[`proc_ui`](#t4-29)）。 | `OSGetForegroundBucket` / `OSGetForegroundBucketFreeArea`。ProcUI はフォアグラウンドを手放す前に、アプリにその中身を退避させる。 |
| <a id="t3-8"></a>3.8 | キャッシュライン | CPU のキャッシュが扱う 32 バイト単位のかたまり。 | 1 すくいの量。 | ゲームの「この範囲を書き戻して」はキャッシュライン単位。shocora はこれで GPU が読み直すべき場所を知る。 | [キャッシュ](#t2-5) が読み書きする最小単位。ここでは 32 バイト（多くの PC では 64）。キャッシュフラッシュの呼び出しはこの単位で動く。 | 32 バイト。`dcbz` は 1 ライン分をゼロにし、`DCFlushRange` はライン単位に丸める。shocora の `WriteTracker` は 4 KiB ページ単位で印を付け、GPU は変わった所だけハッシュし直す。 |
| <a id="t3-9"></a>3.9 | アパーチャ | GPU の画像を、単純な 1 行ずつの並びに見せてくれる窓。 | 覗くとバラバラのジグソーパズルが 1 枚の絵に見える窓。 | 描いた絵をこれで読み出すゲームもある。 | [タイリング](#t5-21) された画像を、普通のピクセル配列のように CPU から読めるようにする仕組み。使われることは少ないが、エミュレータは対応しておく必要がある。 | `GX2AllocateTilingApertureEx` は、アクセス時にタイルを解くハードウェア窓を設定する。shocora はタイル化されたサーフェスの線形ビューを提供する必要がある。 |

## 4. OS（Cafe OS）

ゲームはたいていの場合、ハードウェアを直接いじりません。「スレッドを始める」「メモリを確保する」「ファイルを開く」といった、ゲーム機の **OS**（Cafe OS）が用意した関数を呼びます。shocora は任天堂のコードを動かすのではなく、それらの関数を自前で作り直しています。

| # | 用語 | ひとことで | たとえるなら | なぜ大事か | 中級者向けの詳細 | 専門家向けの詳細 |
| ---: | --- | --- | --- | --- | --- | --- |
| <a id="t4-1"></a>4.1 | OS（オペレーティングシステム） | ハードウェアを管理し、プログラムにサービスを提供する土台のソフト。 | 電気・水道・郵便・鍵を管理するビルの管理会社。 | ゲームはほとんどすべてを OS に頼っている。 | Windows や Linux と同じ役割で、スレッド（[スレッド](#t4-10)）、メモリ、ファイル、タイマーを扱う。ただし小さく、ゲームはライブラリ（[ライブラリ](#t4-5)）のようにリンクする。 | Cafe OS は PowerPC カーネルと、ユーザー空間の RPL ライブラリから成る。ゲーム、HOME メニュー、オーバーレイがプロセスごとのアドレス空間で動くマルチプロセス構成。 |
| <a id="t4-2"></a>4.2 | Cafe OS | Wii U の OS（「Cafe」は開発コードネーム）。 | Wii U のビル管理会社。 | shocora が Rust で作り直している。 | ゲームからカーネルは直接見えない。システムの [RPL](#t4-7)、主に [`coreinit`](#t4-9) がエクスポートする関数を呼ぶ。 | カーネルがスケジューリング、IOSU との IPC、メモリを担当し、`coreinit.rpl` がそれをユーザー向け API（約 2,000 個のエクスポート）として包む。 |
| <a id="t4-3"></a>4.3 | HLE（高レベルエミュレーション） | 下のハードウェアをまねる代わりに、OS の関数を「同じ結果を返す自作の関数」に置き換える方式。 | 古い電話交換機を作り直す代わりに、同じ受け答えをする新しい受付係を雇う。 | shocora（と Cemu）が Wii U の OS を用意するやり方。速く、本物のゲーム機のファイルも不要。 | Linux の Wine が Windows を動かさずに Windows API を作り直しているのと同じ。ゲームがインポートする OS の関数（[インポート / エクスポート](#t4-8)）を、同じことをする Rust のコードに置き換える。 | インポートされた各シンボルは、`wiiu_cafe_os::dispatch` に入るスタブ（`StepEvent::HleCall(index)`）に結び付けられる。`hle_export` マクロが PowerPC ABI（r3〜r10、f1〜f8）からの引数変換を生成する。 |

## 5. グラフィックス（GX2 と Latte）

ゲームは 1 枚の絵を描くとき、自分でピクセルを塗るわけではありません。GPU に「このテクスチャを使って」「このシェーダーを使って」「この三角形を描いて」という長い指示のリストを送ります。GX2 は、その指示を書くための Wii U のライブラリです。

| # | 用語 | ひとことで | たとえるなら | なぜ大事か | 中級者向けの詳細 | 専門家向けの詳細 |
| ---: | --- | --- | --- | --- | --- | --- |
| <a id="t5-1"></a>5.1 | GX2 | Wii U のグラフィックライブラリ。 | 画家への注文書の書式。 | ゲームは GX2 を呼び、shocora はその結果を PC のグラフィックカードでの描画に変える。 | とても薄い OpenGL のようなもの。ドライバを呼ぶ代わりに GPU 自身のコマンド（[PM4](#t5-3)）をメモリに書き込む。ゲームのために検証や状態管理をするドライバはない。 | 薄いユーザーモードドライバ。GX2 の関数がコマンドバッファへ直接 PM4 を書き、`GX2Flush` がカーネルの TCL 経由でコマンドプロセッサに送る。 |

| <a id="t10-1"></a>10.1 | IOSU | セキュリティ用プロセッサ上の小さな OS。ストレージ、USB、ネットワークを担当する。 | ビルの裏方事務所。 | ゲームはここに頼みごとを送る。shocora は直接答える。 | 専用チップ（[Starbuck](#t2-22)）の上で動く 2 つ目の OS で、ストレージとネットワークを握っている。ゲームが触れられるのは [IPC](#t10-2) 経由だけ。 | プロセスを分離した ARM のマイクロカーネルと、リソースマネージャー群。暗号、タイトル管理（MCP）、FS、ネットワーク、USB を扱う。 |
| <a id="t10-2"></a>10.2 | IPC | メイン CPU とセキュリティ用プロセッサの間でやりとりされるメッセージ。 | ドアの下から差し込むメモ。 | 本物のゲーム機では、ファイルやアカウントの依頼はこれで届く。 | ローカルのサーバーを呼ぶようなもの。`open`、`read`、`ioctl` のメッセージを送り、非同期に答えが返る。 | `IOS_Open/Close/Read/Write/Seek/Ioctl/Ioctlv`（コールバック付きの `Async` 版も）を共有メモリの IPC バッファ経由で送る。結果は IPC 割り込みで戻る。 |

## 11. shocora がゲームを動かす仕組み（エミュレータの技術）

| # | 用語 | ひとことで | たとえるなら | なぜ大事か | 中級者向けの詳細 | 専門家向けの詳細 |
| ---: | --- | --- | --- | --- | --- | --- |
| <a id="t11-1"></a>11.1 | インタプリタ | ゲームの命令を 1 つずつ読んで、その通りに実行する。 | スピーチを 1 文ずつ同時通訳する。 | 正確だが遅い。まだ翻訳していないコードやデバッグに使う。 | スクリプト言語のインタプリタ（CPython）と同じで、[命令セット（ISA）](#t2-6) の 1 つずつについてデコード → 実行を繰り返す。 | `interpreter::step` が 1 命令をデコードして実行する。これが基準となる意味論で、JIT は命令単位でここに戻れる（`interpret_one`）。 |
| <a id="t11-2"></a>11.2 | JIT（ジャストインタイムコンパイラ）/ リコンパイラ | ゲームのコードを初めて実行するときにまとめて PC の命令に翻訳し、その後は翻訳を使い回す。 | 本の 1 章を 1 回翻訳したら、あとは翻訳版を読むだけ。 | ゲームのコードのほとんどはこの方法で動く。インタプリタよりずっと速い。 | Java や JavaScript エンジンの JIT と同じだが、入力はバイトコードではなく機械語（[PowerPC](#t2-7)）。翻訳ができるまで新しいコードは [インタプリタ](#t11-1) で動くので、止まりはしないが一時的に遅くなる（[カクつき（スタッター）](#t1-6)）。 | 2 段構成。まず速い翻訳（Cranelift `opt_level=none`、最大 64 命令の直線ブロック）をワーカースレッドに投げ、よく実行されるブロックを最適化リージョンとして翻訳し直す。ブロック同士はページテーブルと末尾呼び出しでつながる。 |
| <a id="t11-3"></a>11.3 | Cranelift | shocora の JIT が PC の命令を作るのに使っているライブラリ。 | 翻訳者の辞書と文法書。 | 翻訳したコードの速さを左右する。 | LLVM のようなコンパイラのバックエンドだが、速くコンパイルできるように作られていて [JIT（ジャストインタイムコンパイラ）/ リコンパイラ](#t11-2) に向いている。 | Bytecode Alliance（Wasmtime）製の SSA ベースのコード生成器。LLVM より大幅に速くコンパイルできる代わりに最適化は少ない。shocora は `tail` 呼び出し規約を使う。 |
| <a id="t11-4"></a>11.4 | ブロック / リージョン | まとめて翻訳する短い命令の並び（ブロック）と、ループなどを含む大きな範囲（リージョン）。 | 1 文と、1 段落。 | よく動くコードは、より速いリージョンとして翻訳し直す。 | [JIT（ジャストインタイムコンパイラ）/ リコンパイラ](#t11-2) が翻訳する単位。リージョンはループ全体を含むので、エミュレータに戻らずに動き続けられる。 | リージョン：分岐をたどった ±16 KiB 以内の最大 256 命令。呼び出しの戻り先に追加のエントリーを持ち、戻りも同じコードの中に着地する。 |
| <a id="t11-5"></a>11.5 | ホットコード | 非常によく実行されるコード。 | 毎日使うフレーズ。 | 丁寧に翻訳する価値がある。起動時に 1 回だけ動いたコードはそうではない。 | 実行時のプロファイルに基づく最適化と同じ。よく実行されるコードだけが、時間のかかる良い翻訳を受ける。 | 速い翻訳のブロックは実行のたびにメモリ上のカウンタを増やし、`HOT_RUNS`（1,000 回）で最適化待ちに入る。ホット判定は候補を 16,384 件ずつ走査する。 |
| <a id="t11-6"></a>11.6 | コードキャッシュ | 翻訳済みのコードを置いておくメモリ。 | 翻訳済み原稿の棚。 | 数百 MB になることもある。shocora はすき間なく詰めて置き、大きくなりすぎたらあまり使われない翻訳を手放す。 | ブラウザの JIT 用メモリと同じで、実行したコードの量に応じて増える。shocora は簡易な翻訳に上限を設け、フレームの合間に解放する（[ワーキングセット / メモリ使用量](#t11-15)）。 | `CodeMemory`（64 MiB チャンク、バッチごとに実行可能化）を使う Cranelift の `JITModule`。速い翻訳は別モジュールに置き、256 MiB を超えたらフレーム境界で解放する。ブレワイでの実測：速い翻訳 約 240 MB、最適化 約 530 MB。 |
| <a id="t11-7"></a>11.7 | マルチコアモード | Wii U の 3 つのコアを、それぞれ別の PC スレッドで同時に動かす。 | 交代で料理するのではなく、3 人同時に料理する。 | Cemu と同じく、CPU 側が最大で 3 倍速くなる。 | ゲストの 3 つの [コア](#t2-3) に 3 本のホストスレッドを割り当て、ゲストメモリを共有する。OS 部分も共有なので [ロック（エミュレータ内部）](#t11-10) で守る。 | フレームごとに、コア 0 と 2 はスコープ付きスレッド、コア 1 は呼び出し元のスレッドで動く。HLE 呼び出しとスケジューリングは 1 つのマシンロックを取り、JIT のページテーブルはロックなしで読む。 |
| <a id="t11-8"></a>11.8 | GPU スレッド | ゲームの描画指示の処理だけを行う PC のスレッド。 | 注文書を仕分ける専任の助手。 | CPU 側が描画を待たずに済む。 | ゲームエンジンのレンダースレッドと同じ。ゲームのスレッドが仕事を積み、GPU スレッドが並行して処理する。 | PM4 を実行して `RenderCommand` を作る。CPU が待つのは `GX2DrawDone`、タイムスタンプ、または `MAX_FRAMES_AHEAD`（2）フレーム先行したときだけ。 |
| <a id="t11-9"></a>11.9 | レンダースレッド | PC のグラフィックカードとやりとりする PC のスレッド。 | 実際に画家へ注文書を渡す係。 | グラフィックドライバの重い処理を、ゲームの処理から切り離す。 | wgpu（[wgpu / Vulkan / DirectX 12](#t5-39)）を呼ぶスレッド。ドライバの呼び出しをここに集めて、エミュレーションのスレッドが遅くならないようにする。 | wgpu のデバイスを持ち、容量 3 の有界チャネルからコマンドの束を受け取る。テクスチャ転送は 32 MiB のステージングリング経由でエンコーダに記録し、アリーナへの書き込みはまとめて行う。 |
| <a id="t11-10"></a>11.10 | ロック（エミュレータ内部） | エミュレータの共有データを、一度に 1 つの PC スレッドだけが変更できるようにする決まり。 | 会議の発言権を示すトーキングスティック。 | 待つほど時間の無駄になる。よく使う処理をロック不要にしたこと（ファストコール）で大きく速くなった。 | エミュレータ自身のコードにある普通のミューテックス（ゲストの [ミューテックス（OSMutex、OSFastMutex）](#t4-17) とは別物）。ゲストの呼び出しのうちこれが必要なものが少ないほど、コア同士の待ち時間が減る（[ファストコール](#t11-11)）。 | `CafeOs`、`Gpu`、`Iosu` を包む `std::sync::Mutex`。プロファイルでコアごとの待ち時間を報告する（`SHOCORA_PROFILE` の `lock`）。 |
| <a id="t11-11"></a>11.11 | ファストコール | 共有のロックなしで動かせるほど単純なシステム関数（メモリコピー、時刻、スレッドのデータなど）。 | 事務所に頼まず、自分の机のペンを取る。 | 3 つのコアがお互いを待たずに済む。 | 呼んだコア自身のデータにしか触れない [HLE（高レベルエミュレーション）](#t4-3) の関数で、[ロック（エミュレータ内部）](#t11-10) を取らずに済む。 | `wiiu_cafe_os::fast`：memcpy / memset、キャッシュ操作、コア番号、時刻、スレッド固有スロット、初回以降の `__tls_get_addr`。書き込みは GPU の書き込み追跡に転送される。どれもロック版と同じ結果になることをテストで確認している。 |
| <a id="t11-12"></a>11.12 | グラフィックパック | 解像度・フレームレート・シェーダーを変える Cemu の追加データ。 | 改造キット。 | shocora は設定画面で似たオプションを提供している。 | Cemu の MOD。シェーダーの差し替え、[解像度倍率](#t11-13) の変更、FPS パッチ。 | `rules.txt` に、シェーダーハッシュをキーにしたシェーダー置き換え、テクスチャサイズに一致する解像度ルール、ゲームコードへのアセンブリパッチを組み合わせたもの。 |
| <a id="t11-13"></a>11.13 | 解像度倍率 | ゲームの絵を、本物の N 倍の大きさで描くこと。 | 写真を大きいサイズで印刷する。 | 絵がくっきりする代わりに、グラフィックカードの時間とメモリを使う。 | ゲーム設定の内部解像度スケールと同じことを、その設定を持たないゲームに適用するもの。 | TV 画面と一致するターゲットだけを拡大し（シャドウマップはそのまま）、幅は最大 10,240 ピクセル。メモリ不足では倍率を下げる。 |
| <a id="t11-14"></a>11.14 | セーブステート | エミュレートしているゲーム機全体の、ある瞬間の丸ごとのスナップショット。 | 映画を一時停止して、その 1 コマを丸ごと保存する。 | ゲーム自身のセーブデータとは別物。 | 仮想マシンのスナップショットと同じ。ある瞬間のマシン全体のメモリと [レジスタ](#t2-9)。 | CPU / OS / GPU の状態を postcard で直列化し、ゲストメモリとホストのサーフェスを lz4 で圧縮して保存する。バージョン付きなので、別ビルドでは読み込めない。 |
| <a id="t11-15"></a>11.15 | ワーキングセット / メモリ使用量 | エミュレータが今、PC の RAM をどれだけ使っているか。 | 作業で机をどれだけ占領しているか。 | 少ないほど、他のソフトのための余裕が残る。 | タスクマネージャーの「メモリ」の列。shocora では主に、ゲストメモリ（[MEM2](#t2-21)）、翻訳済みコード（[コードキャッシュ](#t11-6)）、レンダラのキャッシュ。 | RAM に載っているページ（タスクマネージャーの「メモリ」）。コミット量とは別物。ブレワイでは、ゲストメモリ 約 1.1 GB、JIT コード 約 0.8 GB、残りがヒープとドライバのメモリ。 |
| <a id="t11-16"></a>11.16 | Cemu | C++ で書かれた、最も実績のある Wii U エミュレータ。 | 経験豊富な先輩。 | shocora は Cemu で実績のある方法をよく参考にしている。 | 多くのエミュレータの手法の確認先となる参照実装で、ソースコードは公開されている。 | 2022 年からオープンソース（MPL-2.0）。独自 IR を通した PPC → x86-64 リコンパイラ、非同期シェーダーコンパイル付きの Vulkan / OpenGL による Latte レンダラ、ファイバーでスレッドを実装した HLE の coreinit を持つ。 |
